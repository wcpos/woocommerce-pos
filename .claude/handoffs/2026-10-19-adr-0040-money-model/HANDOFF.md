# Handoff: implement ADR 0040 on the server (money state without an epoch)

**Date:** 2026-10-19 · **Lane:** `next` · **Decision:** `docs/adr/0040-server-derives-paid-no-money-epoch.md` (accepted, merged in #2332) · **Decision owner:** Paul · **Stakes:** High (checkout money) · **Vocabulary:** `GLOSSARY.md` at the repo root (Sale, Tender, Payment row, Balance, Paid, Partial, Reopen, Completion, Fiscal record, Money command, Attempt, Offline tender)

## Why this exists

ADR 0040 replaced the money-epoch design of payments contract 1.3 before it shipped. #2312 (25 Codex rounds) and its carve #2328 (5 rounds) are closed unmerged; the epoch-independent hardening from #2328 is already on `next` (#2336). What remains is the design the ADR describes: the server derives "paid" from its payment rows, money never rides in the pushed order document, reopen is a status change with every payment still counting, every money command is idempotent and revision-checked, and the fiscal side keys on a completion number.

This handoff is for the agent that writes that design and ships it. It states what `next` already does (so nothing is rebuilt), the gap per ADR rule, the questions Paul has to answer before code is written, the PR sequence, and the review stance. Read the ADR in full first; its "Why not the epoch" paragraph is the answer to most review findings this work will attract. Codex reviewed this handoff itself (#2343, fourteen findings, all taken); the gap table below is the corrected version.

## The gap, rule by rule

| ADR rule | Today | Change |
|---|---|---|
| 1a — balance counts **captured** rows and succeeded refunds, and can be negative | `COUNTING_STATUSES` includes `authorized`, so a full-value authorization completes the order (stock, email, `date_paid`) before capture. Balance ignores refunds and clamps at 0. | `paid()` sums `captured` rows only; `authorized` is money in motion (rule 3) and never completes a sale, so the authorize capture mode completes at capture. Pin: a full authorization leaves the order `pos-open` with `summary.authorized` showing the amount; capture completes it. Balance = total − Σ captured + Σ `succeeded` allocations, **signed**: `summary.balance` is the amount still due (clamped) and `summary.refund_due` the amount owed back when the signed balance is negative; a `pending` allocation is shown as `summary.refund_pending`, never added. Pin: 100.00 captured, total reduced to 80.00 → `balance 0.00`, `refund_due 20.00`, and the two states are distinguishable. |
| 1b — `close` command; a reopened sale closes through it | No `close`. `derive()` never re-completes an order outside the in-progress statuses, so a reopened sale is not completed again. | New `close` money command (Q2). It re-derives and, when the signed balance ≤ 0 on a non-zero total, runs the paid transition and writes completion `n+1`; **retained money above a reduced total still completes** (ADR rule 1: covered is covered) and `refund_due` is exposed beside it. `derive()` learns that `close`, and only `close`, may complete an order whose status is an open status outside `IN_PROGRESS_STATUSES`. Pin: paid sale reopened, line removed, `close` → completion `n+1` **and** `refund_due`; reopened unchanged, `close` → completion `n+1` with zero adjustment; a void after completion still never pulls the order back. |
| 1c — the completion stamp, from **every** completion path, with its own provenance | Nothing is stamped per completion; the till's provenance tuple is write-once and describes the first sale only. Webview and gateway-callback completions bypass `derive()`. | One `Completion_Stamp` writer (name is the spec's) hooked on `woocommerce_payment_complete` at a priority **before** `Fiscal_Record_Writers`, and called directly by `derive()` and `close` so the stamp is in the same save as the transition where there is one. It appends `_wcpos_completions[n]` = `{ id (uuid minted by the server), at_gmt, sale_time, sale_tz, register, session, counter, total }` and sets `_wcpos_completed_at`. **Provenance comes from the command that completed the sale**: `record`, `capture`, `submit` and `close` carry `register_id`, `session_id`, `sale_time`, `sale_tz`, `sale_counter` in their body, validated like the till meta; the write-once tuple is the fallback for completion 1 only (and for order-pay, where the webview mint carries the register). Pin: completed on register A, reopened and closed on register B → entry 2 names B; webview completion and gateway-callback completion each write an entry; `wcpos_sale_completed( $order, $n )` fires once per entry, after the stamp is persisted. |
| 2 — money never travels in the push | `set_paid` is the offline cash path; `_wcpos_payments` is forwarded and merged; `payment_method`, `payment_method_title`, `transaction_id`, `date_paid` and any status pass through. | A **server-owned key list**, stripped before the write, by top-level key and as id-addressed meta edits or tombstones (posts storage names the backing meta): `_wcpos_payments`, `_wcpos_payment_method`, `_wcpos_payment_id`, `_wcpos_payment_live`, `_wcpos_commands`, `_wcpos_completed_at`, `_wcpos_completions`, `_wcpos_gateway_attempts`, `_wcpos_awaiting_customer`, `date_paid`, `set_paid`, `transaction_id`, `payment_method`, `payment_method_title`. One constant beside `Pos_Order_Audit::SERVER_META_KEYS`, tested by a push that sends every key (top-level and by meta id) and reads storage back unchanged. **Pushed statuses are restricted to the open set**: `pos-open`, `pending`, `on-hold`, `failed`, `cancelled` (the spec may extend the list; `pos-partial` is derived, never pushed); `processing`, `completed`, `refunded` and every per-gateway POS paid status → 422 `wcpos_status_not_pushable`. Pin: an uncovered order pushed to `processing` stays unpaid, no `date_paid`. **See Q1 before touching `set_paid`.** |
| 3 — reopen is a status change; refused only while money is in motion; atomic | A push can move a completed order to `pos-open` today with nothing checked and no lock. | A status change from a paid status to an open status is accepted when no row is `pending` or `authorized`, no gateway attempt is `sent` without an answer, and no refund allocation is `pending`; otherwise 422 `wcpos_money_in_motion` naming the row. The check runs **under the order lock** (see rule 6b) so a capture cannot land between the check and the write. Rows keep counting; nothing is archived or re-stamped; reopen writes no completion entry. |
| 4 — line edits need `is_editable()` | Not enforced on the push lane. | Before forwarding, if the payload changes `line_items`, `fee_lines`, `shipping_lines`, `coupon_lines` or `tax_lines` and `! $order->is_editable()` on the locked fresh read **and** the payload's `status` does not itself move the order to an editable status in the same push (Q3) → 422 `reopen_required`. |
| 5 — per-command idempotency `(command id, body fingerprint, outcome)`, kept for the life of the row | Only `record` replays, by row id and field comparison. `submit` and `cancel` can succeed with no row to hang an outcome on. | Each of `intent`, `capture`, `void`, `refund` allocation, `cancel`, `submit`, `close` takes a `command_id` (uuid, required at contract 1.3). Row-addressed commands store `(id, fingerprint, outcome)` in a `commands` map **on the row**, keyed by id and **never evicted** while the row exists (the map grows by one entry per distinct command, which is small; `EVENTS_MAX`-style bounding would re-run an evicted `submit`). Row-less commands (`submit`, `cancel`, `close`) store theirs in an order-level `_wcpos_commands` map, server-owned (rule 2), bounded only by removing entries whose attempt is terminal **and** older than the attempt history keeps. Same id + same fingerprint replays the stored outcome; same id + different body → 422 `wcpos_command_conflict`; same id while in flight → 409 `wcpos_payment_locked`. `record` and the webview mint keep the row id as the command id. No new table (`.ai/rules/db-tables.mdc`). |
| 6a — every money command carries the order revision; replay checked first | Push lane has `baseRevision`; money routes have none. | Money routes take `revision` (the hash the push lane compares: `Write_Controller::revision_for()` over `Revision::compute()` / `compute_scoped()`, ADR 0033); replay lookup (rule 5) runs **before** the revision compare; a fresh command with a stale revision → 409 `wcpos_revision_stale` with `currentRevision`. Confirm the hash excludes storage facts (memory `content-hash-must-exclude-storage-facts`) and **includes** the ledger projection the till sees, so a money command moves the revision a later push compares against. |
| 6b — pushes and money commands are serialised | `Order_Writer` takes `Order_Lock` only for a cart restart or a pushed ledger; a line-edit push checks its revision, then a capture completes against the old total, then the push saves a new total. | Any push that changes lines, fees, shipping, coupons, taxes, `status` or the customer **acquires the order lock before the revision compare and holds it through the wc/v3 write** (the same lock the money commands and the ledger keeper hold; a held lock answers the retryable 409 `woo_rxdb_sync_record_locked`, as the ledger push does today). Pin the interleaving: push A reads revision r1; command B captures and completes; push A's locked compare now sees r2 and is refused. Nesting against the `Mutation_Store` record lock keeps the ordering `Order_Writer::forward()` already uses. |
| 7 — gateway payments stay two saves | Already so (sent-before-dispatch, sweeper, #2336). | No change beyond the command id on `submit` and the sweeper asking the provider by the client's reference before any retry (verify it does; `Payments_Sweeper` dispatches only `Ledger::is_unanswered()` rows). |
| 8 — a refund is two saves too, and the record is never deleted after the provider refunded | The allocation is written after `process_refund()`, which answers only a boolean; a save that throws after a successful provider refund loses the allocation and a retry refunds again. | The refund allocation follows rule 7's shape: write the allocation `pending` **with its command id before** `process_refund()`, then `succeeded` / `failed` after. A retry with the same command id finds the pending allocation and does not call the provider again; a stranded `pending` allocation (saved before, no answer recorded) is a reconciliation item: order note "WCPOS: refund … was sent to the provider; confirm before retrying", `summary.refund_pending`, and the sweeper leaves it to a human because the gateway returns no reference to poll. The allocation path never deletes the refund object. Pin with a gateway stub whose `process_refund()` succeeds and a ledger save forced to throw: one provider call across the original and the retry. Confirm from the monorepo that the till creates refunds with `api_refund: false` (the provider refund belongs to the allocation, not to wc/v3); if not, that is a client-handoff item. |
| Fiscal — key on `(order_id, n)` without a schema change | `record()` keys `sale` by `order_id`; a second completion returns the first row. | The `sale` record's replay identity becomes `source_id` = the completion entry's uuid (`_wcpos_completions[n].id`), which the existing `UNIQUE KEY type_source` already guards; `order_id` stays a plain column and index. `find_sale( $order_id )` becomes `find_sale( $order_id, ?string $completion_id = null )` returning the latest when null. Completion `n` writes `sale` record `n` whose payload names `supersedes_record_id` and the signed adjustment (new total − superseded total), carried through the closure `adjustments` counter when a closure already covers the earlier record. The writer condition moves from `wcpos_is_pos_order()` to "has a completion entry" (an online order finished at the counter is a sale at that register). Pin **through `record()`**, not only the reader: two completions on one order insert two `sale` rows with distinct numbers; replaying completion `n` returns row `n`. `late_sale` keeps its `order_id` identity (check whether it also needs the completion id; the spec decides). |
| Contract version | `'1.2'` | `'1.3'` means: server derives paid from captured rows, strips money from pushes, refuses stale revisions on money commands, requires `command_id`. Bump in the **last** PR of the sequence, with the wiki rewrite. |

## Questions for Paul before PR 1 (one at a time, each with a recommendation)

- **Q1 — what happens to a pre-1.3 till's `set_paid` cash sale?** Today a cash sale is `set_paid: true` on the push (ADR 0035 path 3) **unless the shipped app already records cash through `POST orders/{id}/payments`**; the orchestrator could not confirm which from the stale local monorepo clone (its `origin/main` was at #2683 while the ADR cites #2702/#2710 as merged), so the implementing agent checks the monorepo's current `main` first (`gh search code` or a fresh fetch) and reports the answer with the question. Options: (a) strip `set_paid` only from clients that declare `payments=1.3` in `X-WCPOS-Client` (the wiki §13 token) and keep path 3 for older tills until the protocol boundary (memory `fleet-skew-doctrine`: breaking wire changes batch behind one enforced boundary; the web lane is version-paired, only native apps skew); (b) hard cut: strip for everyone and have the till re-send as a `record`. **Recommend (a)**: it is the house pattern and it keeps every shipped till selling. Under (a) the token parser lands in **PR 1** (it is what PR 1 branches on); the advertised contract bump and any 426 enforcement stay in PR 5.
- **Q2 — the `close` route shape.** `POST orders/{id}/close` beside the payments family (recommended: it is a money command and shares their gate, lock, revision and refusal codes) or a push-lane status write that the server treats specially (rejected by the ADR: "the push lane cannot close a sale").
- **Q3 — reopen-and-edit in one push.** A till that pushes `status: pos-open` together with changed lines on a completed order: accept (the status moves first under the lock, `is_editable()` then passes) or refuse with `reopen_required` and make the till send two pushes. **Recommend accept**, with the money-in-motion check (rule 3) run first; it is what a WooCommerce admin edit does in one save.
- **Q4 — the in-progress `status` the till sends** (ADR "still to decide"): honour `pos-open` / `pending` as sent, or ignore and let `derive()` set them. **Recommend ignore for money statuses, honour `pos-open` as the reopen signal and `pending` / `on-hold` / `cancelled` as WooCommerce statuses the cashier may choose**; `derive()` owns `pos-partial` and the paid statuses (rule 2 refuses the paid ones outright).
- **Q5 — original tender of a reopened online order.** When a paid order with an empty ledger is reopened, the server **adopts a persisted row** from `payment_method`, `payment_method_title`, `_transaction_id` and `date_paid` (`status: captured`, `source: woocommerce`, amount = total at reopen, through `Ledger::adopt()` exactly as the webview mint does), so the row keeps counting after the cashier records a differential tender; a read-only synthetic row would vanish the moment the ledger is non-empty and the server would collect the original amount again. The row is never voidable from the till (its money lives at the online gateway) and refunds against it go through the gateway's `process_refund()` like any captured row. **Recommend yes, adopted at reopen.** Pin: 100.00 paid online, reopened, total 110.00, 10.00 recorded → balance 0.00, both rows present.
- **Q6 — `authorized` stops counting as paid** (rule 1a). This is the ADR's text, but it changes the authorize capture mode's visible behaviour on `next`: the sale completes at capture, not at authorization. Paul confirms before PR 2; if he wants authorization to complete the sale, the ADR's rule 1 wording is amended in the same PR, not silently.

Ask them in that order; each answer changes PR 1 or PR 2. Do not start PR 1 before Q1 is answered.
