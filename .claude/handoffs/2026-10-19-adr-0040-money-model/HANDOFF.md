# Handoff: implement ADR 0040 on the server (money state without an epoch)

**Date:** 2026-10-19 · **Lane:** `next` · **Decision:** `docs/adr/0040-server-derives-paid-no-money-epoch.md` (accepted, merged in #2332) · **Decision owner:** Paul · **Stakes:** High (checkout money) · **Vocabulary:** `GLOSSARY.md` at the repo root (Sale, Tender, Payment row, Balance, Paid, Partial, Reopen, Completion, Fiscal record, Money command, Attempt, Offline tender)

## Why this exists

ADR 0040 replaced the money-epoch design of payments contract 1.3 before it shipped. #2312 (25 Codex rounds) and its carve #2328 (5 rounds) are closed unmerged; the epoch-independent hardening from #2328 is already on `next` (#2336). What remains is the design the ADR describes: the server derives "paid" from its payment rows, money never rides in the pushed order document, reopen is a status change with every payment still counting, every money command is idempotent and revision-checked, and the fiscal side keys on a completion number.

This handoff is for the agent that writes that design and ships it. It states what `next` already does (so nothing is rebuilt), the gap per ADR rule, the questions Paul has to answer before code is written, the PR sequence, and the review stance. Read the ADR in full first; its "Why not the epoch" paragraph is the answer to most review findings this work will attract.

## The gap, rule by rule

| ADR rule | Today | Change |
|---|---|---|
| 1 — balance counts succeeded refunds; `close` command; completion stamp written by the server | Balance ignores refunds. No `close`. `derive()` never re-completes an order outside the in-progress statuses, so a reopened sale closed unchanged is not completed again. No `_wcpos_completions`; `_wcpos_sale_time` and friends are till-supplied, write-once. | `balance()` adds Σ `succeeded` allocations across rows; `summary` shows pending reservations beside the balance, never in it. New `close` money command (route under the order's payments family) that re-derives and runs the paid transition when covered; `derive()` learns that `close` (and only `close`) may complete an order whose status is an open status but outside `IN_PROGRESS_STATUSES`. On every paid transition the server appends `_wcpos_completions[n]` (sale time + zone, register, session, counter, total) and sets `_wcpos_completed_at`; `n` is the array index + 1. The till-supplied provenance tuple stays as the register identity the stamp copies from. |
| 2 — money never travels in the push | `set_paid` is the offline cash path; `_wcpos_payments` is forwarded and merged; `date_paid` / `transaction_id` are not stripped. | A **server-owned key list** stripped before the write, by key and as id-addressed edits or tombstones: `_wcpos_payments`, `_wcpos_payment_method`, `_wcpos_payment_id`, `_wcpos_payment_live`, `_wcpos_completed_at`, `_wcpos_completions`, `_wcpos_gateway_attempts` (`Gateway_Submission::ATTEMPTS_META_KEY`), `_wcpos_awaiting_customer`, `date_paid`, `set_paid`, `transaction_id`. One constant beside `Pos_Order_Audit::SERVER_META_KEYS`, tested by a push that sends each key and reads storage back unchanged. **See Q1 below before touching `set_paid`.** |
| 3 — reopen is a status change; refused only while money is in motion | A push can move a completed order to `pos-open` today with nothing checked; `cart_restart_gmt()` handles the `pos-open` restart. | A status change from a paid/completed status to an open status is accepted when no row is `pending` or `authorized`, no gateway attempt is unresolved (`sent` with no answer), and no refund allocation is `pending`; otherwise 422 `wcpos_money_in_motion` (push lane) naming the row. Rows keep counting; nothing is archived or re-stamped. Reopen writes no completion entry. |
| 4 — line edits need `is_editable()` | Not enforced on the push lane. | Before forwarding, if the payload changes `line_items`, `fee_lines`, `shipping_lines`, `coupon_lines` or `tax_lines` and `! $order->is_editable()` on the fresh pre-read **and** the payload's `status` does not itself move the order to an editable status in the same push → 422 `reopen_required`. Decide (Q3) whether a push carrying both the reopen status and the line change is one write or two. |
| 5 — per-command idempotency `(command id, body fingerprint, outcome)` | Only `record` replays, by row id and field comparison. | Each of `intent`, `capture`, `void`, `refund` allocation, `cancel`, `submit`, `close` takes a `command_id` (uuid, required at contract 1.3); the row (or the order, for `close`) keeps a bounded `commands` history of `(id, fingerprint, outcome)`; same id + same fingerprint replays the stored outcome; same id + different body → 422 `wcpos_command_conflict`; same id while in flight → 409 `wcpos_payment_locked`. `record` and the webview mint keep the row id as the command id. Bound the history like `EVENTS_MAX`. No new table (`.ai/rules/db-tables.mdc`). |
| 6 — every money command carries the order revision; replay checked first | Push lane has `baseRevision`; money routes have none. | Money routes take `revision` (the `Revision` content hash the push lane uses, ADR 0033); replay lookup (rule 5) runs **before** the revision compare; a fresh command with a stale revision → 409 `wcpos_revision_stale` with `currentRevision`. Confirm the hash the push lane compares (`Write_Controller::revision_for()` over `Revision::compute()` / `compute_scoped()`) excludes storage facts (memory `content-hash-must-exclude-storage-facts`) so a ledger write that changes only server-owned meta still moves the revision the till sees. |
| 7 — gateway payments stay two saves | Already so (sent-before-dispatch, sweeper, #2336). | No change beyond the command id on `submit` and the sweeper asking the provider by the client's reference before any retry (verify it does). |
| 8 — refund record never deleted after the gateway refunded | The till creates the WooCommerce refund object first (wc/v3 `orders/{id}/refunds`), then `POST payments/{uuid}/refund` with `refund_id` and `amount` allocates it to a row: `Ledger::refund()` → the row's handler → `Gateway_Handler::refund()` → `->process_refund()`; `Manual_Handler` marks the allocation succeeded at once. Core's deleting `catch` in `wc_create_refund()` runs only when the refund is created with `api_refund: true`. | Two things to pin: (i) the allocation path never deletes the refund object and, when the ledger save throws **after** `process_refund()` returned true, records the allocation `succeeded` (or `pending` with a provider ref) and adds the order note "WCPOS: refund … succeeded at the provider but the ledger write failed; needs attention", so the money is never refunded twice on retry; (ii) confirm from the monorepo that the till creates refunds with `api_refund: false` (the provider refund belongs to the allocation, not to wc/v3), and if it does not, that is a client-handoff item. Pin (i) with a gateway stub whose `process_refund()` succeeds and a ledger save forced to throw. |
| Fiscal — key on `(order_id, n)` | One sale row per order, found by `find_sale( order_id )`; `late_sale` corrects it under a closure. | `record_sale()` runs per completion: completion `n` writes `sale` record `n` whose payload names the record it supersedes (`supersedes_record_id`), with the signed adjustment (new total − superseded total) through the closure `adjustments` counter when a closure already covers the earlier record; `find_sale()` becomes `find_sale( order_id, n )` plus "latest". Writer condition moves from `wcpos_is_pos_order()` to "completed through a register" (the completion stamp carries a register), so an online order finished at the counter is a sale at that register. Fire `wcpos_sale_completed( $order, $n )` for the country modules. This is a change to unlanded design, not to data, but it does touch `Fiscal_Record_Store` reads: check `tests/includes/Services/Test_Fiscal_Record_*` and the table-audit handoff before changing a query. |
| Contract version | `'1.2'` | `'1.3'` means: server derives paid, strips money from pushes, refuses stale revisions on money commands, requires `command_id`. Bump in the **last** PR of the sequence, with the wiki rewrite. |

## Questions for Paul before PR 1 (one at a time, each with a recommendation)

- **Q1 — what happens to a pre-1.3 till's `set_paid` cash sale?** Today a cash sale is `set_paid: true` on the push (ADR 0035 path 3) **unless the shipped app already records cash through `POST orders/{id}/payments`**; the orchestrator could not confirm which from the stale local monorepo clone (its `origin/main` was at #2683 while the ADR cites #2702/#2710 as merged), so the implementing agent checks the monorepo's current `main` first (`gh search code` or a fresh fetch) and reports the answer with the question. Options: (a) strip `set_paid` only from clients that declare `payments=1.3` in `X-WCPOS-Client` (the wiki §13 token, not built on `next`) and keep path 3 for older tills until the protocol boundary (memory `fleet-skew-doctrine`: breaking wire changes batch behind one enforced boundary; the web lane is version-paired, only native apps skew); (b) hard cut: strip for everyone and have the till re-send as a `record`. **Recommend (a)**: it is the house pattern and it keeps every shipped till selling.
- **Q2 — the `close` route shape.** `POST orders/{id}/close` beside the payments family (recommended: it is a money command and shares their gate, lock and refusal codes) or a push-lane status write that the server treats specially (rejected by the ADR: "the push lane cannot close a sale").
- **Q3 — reopen-and-edit in one push.** A till that pushes `status: pos-open` together with changed lines on a completed order: accept (the status moves first, `is_editable()` then passes) or refuse with `reopen_required` and make the till send two pushes. **Recommend accept**, with the money-in-motion check (rule 3) run first; it is what a WooCommerce admin edit does in one save.
- **Q4 — the in-progress `status` the till sends** (ADR "still to decide"): honour `pos-open` / `pos-partial` / `pending` as sent, or ignore and let `derive()` set them. **Recommend ignore for money statuses, honour for `pos-open` as the reopen signal**; `derive()` is the owner of partial/pending.
- **Q5 — original tender of a reopened online order.** Synthetic ledger row from `_transaction_id` and `payment_method` when the ledger is empty on a paid order (the webview passthrough already does this for order-pay), so the till shows what was paid and the balance after the edit is right. **Recommend yes, read-only row `source: woocommerce`**, never saved.

Ask them in that order; each answer changes PR 1 or PR 2. Do not start PR 1 before Q1 is answered.

## How to do it

2. **Worktree off `origin/next`** (never the main tree; `git pull origin next` first): `git worktree add ../woocommerce-pos-worktrees/adr-0040-<pr> -b feat/adr-0040-<pr> origin/next`, own wp-env ports via a gitignored `.wp-env.override.json` mapping the plugin to `woocommerce-pos`. One worktree and one wp-env stack at a time.
3. **PR sequence, each merged before the next branches** (no stacking; memory `feedback_no_stacked_prs`):
   - **PR 1 — push lane**: server-owned key strip (rule 2, per Q1), `is_editable` gate (rule 4, per Q3), money-in-motion reopen refusal (rule 3). Tests: a push carrying each server-owned key leaves storage unchanged (read back with `read_meta()`); a line edit on a `processing` order → 422 `reopen_required`; reopen with a `pending` row → 422 `wcpos_money_in_motion`; reopen of a paid sale with captured rows → accepted, rows unchanged, balance unchanged.
   - **PR 2 — ledger**: refund rollup in `balance()` (rule 1), `_wcpos_completions[n]` + `_wcpos_completed_at` on the paid transition, `close` command (Q2), `derive()` completing a reopened sale through `close`.    - **PR 3 — command idempotency and revision** (rules 5, 6): `command_id` on every money route, history on the row, `revision` parameter, replay-before-revision. Tests: same id + body replays the outcome with a stale revision; same id + different body → 422; in-flight → 409; stale revision on a fresh command → 409 with `currentRevision`; an offline cash `record` replayed after the order's revision moved creates one row.
   - **PR 4 — refund record rule** (rule 8) and the sweeper's provider lookup check (rule 7).
   - **PR 5 — fiscal completion key** (`(order_id, n)`, `wcpos_sale_completed`, writer condition "completed through a register"), `contract: '1.3'` in `Descriptor_Builder`, and, if Q1 chose (a), the `payments=` token in `Client_Signal` with its gate. ## Rules in force

- Fable orchestrates; Codex (`-m gpt-6-astra`, effort high) or an Opus 5.5 Agent implements anything over ~20 lines (the Codex sandbox has no Docker, so PHPUnit runs stay with the orchestrator or an Agent with wp-env). - Order data through the order object only (HPOS; `Order_Postmeta_Guard` fails the test). `Logger`, not `error_log()`.
- **No new table, column or option** without Paul's yes before it is briefed (`.ai/rules/db-tables.mdc`, `.claude/handoffs/2026-10-19-table-audit/HANDOFF.md`). This design adds none: the command history and completion entries are order meta on keys the server already owns.
- Assert code behaviour only after reading it. Both Codex passes on #2322 found claims written from memory that the code contradicted; the ground-truth table above was read from `origin/next` on 2026-10-19 and goes stale.
- Every bug found is fixed in the stream or its own PR; Found is not a parking lot. End every run with Blocked on you / Changed / Found and say whether the session can be cleared.
