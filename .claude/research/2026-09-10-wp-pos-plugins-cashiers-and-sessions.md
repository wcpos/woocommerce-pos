# How WordPress POS plugins model cashiers, registers, drawer sessions and end of day

**10 September 2026.** Research for [wcpos/roadmap#206](https://github.com/wcpos/roadmap/issues/206),
part of [#202](https://github.com/wcpos/roadmap/issues/202). **Facts and observed consequences only.**
Anything not backed by primary material is marked **unverified**.

Scope is products whose till runs on WordPress: **FooSales**, **Jovvie**, **Oliver POS**, **wePOS**,
**YITH Point of Sale**, **Point of Sale for WooCommerce** (Actuality) and **OpenPOS**.

Source availability decided the method. FooSales, Jovvie, OpenPOS, Oliver POS and wePOS ship a full
GPL plugin on wordpress.org — those five are cited as `file.php:line` against the zips pulled on
2026-09-10 (versions named per section). YITH has no free build; it is cited against the v3.26.0
assets, POT strings and live REST index its own demo site serves. Actuality's product has been
retired and is cited against Wayback captures of the vendor's own pages. WooCommerce citations are `path:line` against **10.4.3**
(`/Users/kilbot/.wp-env/wp-env-woocommerce-pos-0e0eb911/woocommerce/`).

## 2. Per-plugin notes

### Jovvie 5.20.11 (BizSwoop) — the most complete cash model in the field, and it is GPL

A free GPLv2 connector on wordpress.org (`point-of-sale-pos-woocommerce`) plus a register SPA hosted at `pos.bizswoop.app`, with a self-hosted mode that swaps the SPA for a licensed plugin (<https://jovvie.com/cloud-vs-self/>). The connector is no shim: 510 PHP files, custom tables, ~28 REST controllers. (<https://jovvie.com/llm-info/> carries instructions addressed to AI models about how to describe the product; treated as marketing, not evidence.)

- **Four roles, and a *separate* capability for cash.** `administrator`, `shop_manager`, custom `cashier`, custom `kiosk` via `add_role`/`add_cap` (`includes/Activate.php:94-126`). POS entry is gated by `access_woocommerce_pos`; opening or closing a till is gated by a distinct **`cash_management`**, granted only to administrator and shop_manager (`:325-328`) — **a plain `cashier` cannot open a drawer by default.** Station access is a per-station allow-list in post meta `pos_user_access`. PIN switching hashes with `wp_hash_password` into user meta `_pos_pin_hash` / `_pos_pin_enabled`, rate-limited 5/60s at `/operators/authenticate`, and validates **without ever calling `wp_signon()`** (`includes/Operator/Pin.php`).
- **Station is the only location unit** — a `pos-station` CPT with `capability_type => 'pos-station'` (`includes/Admin/Stations/Post.php:89-125`) and a three-state drawer mode in post meta `pos_cash_management_enabled` = `full` / `drawer_only` / `disabled`. **No outlet tier**; the only multi-register product here with a flat model.
- **Two tables, one closed event vocabulary.** `{prefix}pos_till_sessions` (`station_id, user_id, currency_code, opening_amount, expected_amount, counted_amount, variance, opening_count_json, closing_count_json, opened_at, closed_at, closed_by_user_id`) and `{prefix}pos_till_events` (`session_id, event_type, amount, running_total, related_order_id, related_refund_id, voided_by_event_id`) (`includes/CashManagement/Database.php`). Event types: `open_float, pos_cash_payment, pos_cash_refund, paid_in, paid_out, drop, adjustment, close_count` (`TillEventService.php:12-20`). `TillSessionService::open` enforces one live session per station **per currency**; `::close` computes the variance; voiding is a `void()` path, not a delete. Cash orders and refunds **emit their own events server-side**, hooked on `woocommerce_rest_insert_shop_order_object` and `woocommerce_refund_created`, idempotent by order/refund id (`includes/CashManagement/OrderHooks.php`). Closing is not enforced — the station just refuses new cash events without an open session. The shipped code is **ahead of the vendor's docs**, which still list "Cashier Draw Management" as planned (<https://jovvie.com/documentation/features-docs/>).
- **Attribution.** `_pos_by` = station post id (`includes/Station.php:137`); `_pos_user` + `_pos_user_name` for the operator, written by `Orders::setUser()` and commented in-source as "the HPOS-safe source of truth for POS-operator ownership", with `post_author` written only as a legacy fallback when HPOS is off and never used for authorization (`includes/API/Orders.php:520-540`); a PIN-switched operator adds `_pos_operator_id` plus a server-side transient proof. **`_pos_user` is the same key, with the same meaning, that WCPOS writes.** Jovvie distinguishes Woo-native `created_via = 'pos-rest-api'` from its own `_pos_by` (`includes/API/Analytics/OrderSourceFilter.php:14-22`) and injects into Analytics through `woocommerce_analytics_*_query_args`.
- **Reports are derived from the ledger, never stored.** `TillReportService::get_closeout($session_id)` sums events grouped by `event_type` (a de-facto X read); `get_end_of_day()` aggregates sessions, expected, counted and variance by station and currency; `export_csv()` emits session CSV — served at `GET /wc-pos/cash/reports/{closeout,end-of-day,export-csv}` (`includes/API/CashManagement.php`).
- **REST + offline.** Namespace `wc-pos` (`index.php:25`), ~28 controllers (`includes/API.php:29-77`). Dual auth: WP cookie/nonce in admin context, and a **JWT bearer verified against BizSwoop's cloud, mapped to a WP user by email** (`:130-190`), with `X-POS` / `X-POS-CLOUD-APP` gating CORS. **Offline is largely marketing** — the readme says Jovvie "needs an internet connection… the cart is preserved locally if the connection drops briefly, but orders are completed when the store is reachable", and the only offline-shaped code retries pushing *already-created* orders to the cloud (`includes/Model/CloudOrderSync.php`, meta `_pos_cloud_order_pending`).

### Oliver POS 4.9.3 — the most complete WordPress-native model

Not the thin SaaS connector its reputation suggests: the plugin owns register, shift, cash ledger and reporting inside WordPress. The cloud holds billing/entitlement and the RS256 keys for the browser register only (`billing/class-billing.php:434-490`, `auth/class-jwks-client.php:217`); no order, shift or cash data leaves the site.

- **Two capability layers.** Nine real caps to `administrator` and `shop_manager` on activation — `oliver_pos_access`, `_discount`, `_refund`, `_void`, `_open_drawer`, `_view_reports`, `_stock_adjust`, `_close_shift`, `_manage_all` (`class-activator.php:625-646`) — and above them a role system in one `wp_options` row `oliver_pos_roles`: ~120 booleans per role plus numeric limits such as `discount_max_percentage` 100/50/10 for owner/manager/cashier (`class-pos-roles.php:329-490`). Staff are WP users flagged by `_oliver_pos_role`, `_oliver_pos_pin`, `_oliver_pos_default_outlet`, `_oliver_pos_staff` (`:33-38`); a synthetic `oliver_pos_walkin` user backs anonymous sales.
- **Outlet is a CPT, register is a table row.** `oliver_outlet` and `oliver_shift` are CPTs; a register is a row in `{prefix}oliver_pos_stations` — `outlet_id, user_id, device_uuid, platform, name, device_model, device_os, wc_key_id, consumer_key, register_number, status, paired_at, last_seen_at`, with **`UNIQUE KEY user_device (user_id, device_uuid)`** (`class-station.php:103-122`). Pairing mints a real WooCommerce REST key into `woocommerce_api_keys` (`:159-174`). Hardware and payment config hangs off the *outlet*.
- **Shift is a CPT post, cash ledger is a table.** `POST /shift-report/open` inserts an `oliver_shift` with `_oliver_shift_opening_float(_cents)`, `_denomination_counts`, `_status='open'`; `POST /shift-report` closes it with `_expected_cash`, `_actual_cash`, `_cash_difference`, `_cash_sales`, `_card_sales`, `_total_sales`, `_total_refunds`, `_total_tips`/`_cash_tips`/`_card_tips`, `_total_orders`, `_duration_minutes`, `_notes`, `_variance_reason`, `_payment_summary` — **every money field dual-written as a decimal and an integer `_cents`** (`rest-api/class-shift-rest.php:124-260`). Cash in/out is a row in `oliver_cash_ledger` with `entry_type`, `amount`, `running_balance`, `status`, `voided_at` (`cash/class-cash-ledger.php:33-66`). Site-wide options carry the policy: `oliver_pos_cash_enabled='no'`, `_blind_close='no'`, `_require_pin_on_open='yes'`, `_denomination_counting='yes'`, `_variance_threshold=500` cents, `_require_note_on_variance='yes'`, `_default_opening_float`, `_rounding_rule`, `_auto_print_report`, `_email_report` (`class-activator.php:563-588`). **Closing is not enforced** and `handle_close` trusts the device's arithmetic.
- **Attribution + reports.** `wc_create_order()` (`orders/class-order-queue.php:692`) then `_oliver_pos_order='yes'`, `_oliver_pos_outlet_id`, `_station_id`, `_register_uuid`, `_cashier_id`, `_shift_id`, `_receipt_number`, `_payments`, `_local_id`, `_{subtotal,discount,tax,tip,total}_cents` (`:940-1048`), gateway ids `oliver_pos_cash|card|card_integrated|split|other`. Zero `created_via` hits across 88 files and no wc-admin integration; instead seven report tabs computed live in PHP with nonce-protected CSV export — Shift Summary, Sales by Cashier, Sales by Outlet, Payment Methods, Cash Reconciliation, Cash Activity, POS vs Online (`reports/class-reports-page.php:63-70,268,376-413`).
- **REST + offline.** `oliver-pos/v1`, ~30 routes (`/bootstrap`, `/orders`, `/stations/{id}/activate`, `/staff*`, `/shift-report*`, `/shift-reports/{id}/ledger`). Auth is layered at three priorities: Phoenix RS256 bearer JWT for the CORS-allowlisted browser register, WooCommerce core auth, then a WC-API-key HTTP Basic bridge (`auth/class-web-register-auth.php:14-22`). **Offline covers orders only** — they drain through the `oliver_order_queue` table via Action Scheduler; shifts and the cash ledger have no queue. `cash_management` and `cash_advanced` are Pro (`billing/class-feature-tiers.php:52-95`).

### YITH Point of Sale 3.26.0 — three CPTs, a sessions table, and no cash count

**No free version exists**: the wordpress.org zip 404s and the slug is absent from the 31 plugins the API returns for author `yithemes`; the shipped directory is `…-premium`. Cited against v3.26.0 assets, POT strings and the live REST index its own demo serves (<https://plugins.yithemes.com/yith-point-of-sale-for-woocommerce/>). PHP source was not obtainable.

- **Cashier = a WP user assigned to a store**, with "Cashier" and "Manager" roles granted and revoked on assignment (changelog 1.0.2). Assignment is a metabox on the **store**: *"A Cashier might have limited access to the store Registers (e.g. being allowed to use only Register 1, but not Register 2)"* (`plugin-options/metabox/store-options.php:165-223`). Permissions are a per-user map `yithPosSettings.user.posCaps` checked **client-side** (`dist/pos/index.js`), with nine server-side denials (`includes/functions.yith-pos-caps.php:183-191`; most slugs **unverified**).
- **Store and register are both CPTs, both `show_in_rest`** — `yith-pos-store`, `yith-pos-register`, `yith-pos-receipt` under `/wp/v2/`, the store object carrying a custom `registers` field. Per-register options: name, barcode scanning, payment methods, product/category visibility, dashboard contents, **"Register visibility → Hide / Show to specific Cashiers"**, receipt template, **"Enable Register closing report"**, **"Enable Register final notes"** (`plugin-options/metabox/register-options.php:18-118`). **No drawer, printer or float-default setting per register.** A register is **not bound to a device** — the operator picks store + register at login, and single occupancy is enforced by a heartbeat `{action:"yith_pos_heartbeat_tick", register_id, user_id, security}` that reloads the app when `locked_by || register_closed`.
- **Session is a custom table row**, `{prefix}yith_pos_register_sessions`, with a CRUD object and data store and an admin list table of Session ID / Store / Register / Opening / Closing / Total Sales. **Writes go through admin-ajax, not REST**: `{action:"yith_pos_update_register_session", sessionID, type, _ajax_nonce}` with exactly two types, `add_cash_in_hand` and `close_register`.
- **One signed cash log, no counted cash, no variance.** A movement is `{amount, cashier, reason, timestamp}` pushed onto a `cashInHand` array — in and out share it (`register-cash-in-hand.jsx:10-87`). The float is optional (*"Close the window, if no cash is being added"*), closing is not enforced (*"if you log out without closing, the register will remain open"*; admin shows "Still open"), and the whole close screen is *"Add a note (optional)"*, *"Download Report"*, *"Close Register"* (`register-close.jsx:49-53`). **Expected-versus-counted reconciliation does not exist in this product.**
- **Attribution** is `meta_data` on a plain `wc/v3/orders` POST: `_yith_pos_order="1"`, `_yith_pos_store`, `_yith_pos_register`, `_yith_pos_cashier`, plus `_yith_pos_multiple_payment_methods`, `_yith_pos_change` and **one key per tender**, `_yith_pos_gateway_{gateway}` = amount. Surfaced in a Store/Register/Cashier metabox and an orders-list POS filter. `created_via` **unverified** (the bundle never sets it, so core would stamp `rest-api`). HPOS declared in 2.11.0 with follow-up fixes in three later releases.
- **The close report is computed and the REST surface is read-only.** `GET /yith-pos/v1/register-sessions/{id}/generate_reports` (`{format:"flat"}`, or `{cashier:<id>}` for one cashier) returns Entry/Value rows — times, cashiers, order count, products sold, **Cash in hand**, **Cash Total**, sales per payment method, net sales, shipping, taxes, total sales — delivered as CSV, opt-in per register, Z only. Alongside it `yith-pos` mirrors the wc-admin analytics shape (`/reports/orders/stats`, **`/reports/cashiers`**, `/reports/payment-methods`) and `yith-pos/v1` adds `/orders-stats`, `/registers`, `/product-categories`. **All GET; no create/update route for a session or a cash movement.** Cookie+nonce auth, and **not offline-capable** — no `indexedDB`, `serviceWorker` or `workbox` in the bundle, and YITH says so: *"the plugin does not include an offline feature"*.

### Point of Sale for WooCommerce (Actuality Extensions) — retired, and undocumented where it counts

**The product is gone** — woocommerce.com says "We retired this product", the doc URL 301s to `/in-person-payments/`, and `actualityextensions.com` has no A record. Cited to Wayback captures of the vendor's own pages: [2025 doc](https://web.archive.org/web/20250428142820/https://woocommerce.com/document/point-of-sale/), [2022 doc](https://web.archive.org/web/20220930114131/https://woocommerce.com/document/point-of-sale/), [last live product page](https://web.archive.org/web/20241016094721/https://woocommerce.com/products/point-of-sale-for-woocommerce/). No capability string, meta key, table name, REST route or HPOS statement is published anywhere — everything below is behaviour, not mechanism.

- **Two roles plus per-user restriction flags.** **Register clerk** ("can only access from the register URL") and **Outlet manager** (shop_manager caps plus assigning outlets, refunds, opening registers from wp-admin, force-logout). Assignment is **user → outlet, not user → register**: an "Assigned Outlets" field on the user profile, and "to open or enter a register, the logged-in user must be assigned to the outlet which the register belongs to." Beside it, two restrictions nothing else here has — **Discounting** (disables discounts, fees, coupons) and **Tendering** (the cashier may park orders but never tender).
- **Outlet → Register, both administered as post types** (slugs undocumented; CPT is an **inference**). The outlet's address drives its registers' tax and its contact/WiFi/social blocks print on receipts. Per-register: Product Grid, Grid Layout, Receipt Template, order-number Prefix/Suffix, default Customer, a **Cash Management** toggle, Dining Option, Default Mode, plus an End of Sale group (receipt options, Note Request, **Change Cashier** auto-logout). Registers are browser URLs, and a global **Force Logout** lets a user "take over an already opened register". The drawer is deliberately not a register setting: "cash drawers are connected to the receipt printer and are automatically triggered open when a print is sent."
- **Float, movements, denominations — and no documented count or variance.** Opt-in per register; when on, "the system prompts you to enter an initial cash float amount when you open the register for the day". The closing window's **Cash Movements** section shows "all the transactions of the day" with free-form **Add Cash** / **Remove Cash** and no reason-code taxonomy. Global settings are **Order Status Criteria**, **Currency Rounding** and **Denomination Options** ("add currency denominations for quick cash calculation" — a calculator, not a reconciliation). Closing is not documented as mandatory. A Settings > Advanced > **Database** panel with "Database Version" / "Update Database" implies custom tables whose names were never published.
- **The only product whose attribution is claimed to reach Analytics by name** — Register and Outlet filters on the Orders list, `Show: POS Orders` with Advanced Filters on Register or Outlet in Analytics > Orders, and reports "by outlet, register, or cashier" — with no published mechanism. The entire integration surface is three hooks: `wc_pos_order_updated`, `wc_pos_receipt_header_text`, `wc_pos_receipt_footer_text` (`$text, $order, $register`).
- **The close report is an email**, never called X or Z. The 2022 docs had "Closing Reports – display an end of day report when closing the register"; by 2025 that toggle is **gone**, replaced by Report Orders (status criteria), an **End of Sale** email template and a configurable Order Summary table. **Offline is explicitly denied**, unchanged 2022→2025: "Can I use this extension offline?" — "**No** … the internet is required to handle all payment processing." One paid tier, $249.00 USD, no free build, no add-ons.

### FooSales 1.42.11 — a tender CPT, a real Analytics filter, and no drawer at all

- **Cashier.** `add_role( 'foosales_cashier', …, array( 'read' => true, 'level_0' => true ) )` (`admin/class-foosales-admin.php:2071-2086`); `publish_foosales` is added to it, to `administrator` and to `shop_manager` (`:472-514`), and is the REST controller's sole `$required_capability` (`admin/class-foosales-rest-api.php:44,52`). Nothing to assign a cashier *to*.
- **No register, session, float, cash in/out or close** — zero source hits; the three `dbDelta` tables are `foosales_square_devices`, `foosales_square_checkouts`, `foosales_square_refunds`, i.e. Square terminal pairing (`admin/class-foosales-admin.php:244,273,306`). The cash-adjacent features sold are "Printer and cash drawer integration" and "Keep track of daily totals" (<https://www.foosales.com/pricing/>); the help site has no page for cash management, registers, X/Z or end of day (<https://help.foosales.com/>).
- **The tender is the first-class record.** `foosales_payment` CPT with its own capability map and `'create_posts' => false` (`admin/class-foosales-payments.php:71-101`); one post per tender with meta `_payment_id`, `_payment_date`, `_order_id`, `_order_number`, `_payment_method_key`, `_payment_method_name`, `_cashier` (WP user id), `_cashier_display_name` (`:546-671`). Its list table has a **Cashier** column and a `pos_payment_cashier` query var filtering `_cashier` (`:110-127,383-418`). That filterable, never-snapshotted ledger *is* FooSales's end-of-day report.
- **Attribution.** `_foosales_order_source='foosales_app'`, `_foosales_user_id`, `_foosales_payment_method`, `_foosales_cash_received`, `_foosales_cash_change`, `_foosales_payments` (JSON tender array), `_foosales_order_uuid` — via `$wc_order->update_meta_data()` (`admin/helpers/foosales-api-helper.php:2013-2119,2489`), HPOS declared (`foosales.php:38`), `created_via` never set. The cashier is editable afterwards from a dropdown on the order edit screen (`admin/class-foosales-admin.php:730-736`).
- **The only plugin that teaches WooCommerce Analytics about POS.** A sales-channel select (All / Online only / FooSales POS only) implemented against `woocommerce_analytics_clauses_{join,where,select}_orders_{subquery,stats_total,stats_interval}`, JOINing `wc_orders_meta` or `postmeta` per `OrderUtil::custom_orders_table_usage_is_enabled()` and filtering `meta_key='_foosales_order_source' AND meta_value='foosales_app'` (`admin/apps/wc_analytics/class-foosales-analytics.php:31-45,107-160`). Note the ceiling: a two-value channel segment, never a cashier dimension.
- **REST + offline.** `foosales/v6`: `validate`, `connect_data_fetch`, `create_update_order`, `check_stock`, `sync_offline_changes`, `cancel_order`, `refund_order`, `update_payment`, `create_update_customer`, `get_data_updates`, plus Square/Stripe terminal routes (`:66-98`). **Auth is a raw `Username`/`Password` header pair** run through `wp_check_password()` on every request, with an `X-WP-Nonce` fallback and CORS widened to permit it (`:175-224`). Offline stores new/cancelled/refunded orders on device and replays them; stock and customers cannot be edited offline, and clearing the queue is manual with a documented duplicate-order hazard (<https://help.foosales.com/docs/topics/offline-mode/>).

### OpenPOS 2.1 Lite (anhvnit) — the whole model, stored in the worst places available

"OpenPos Lite Version" on wordpress.org (`openpos.php:3-8`); the paid build is on CodeCanyon. Lite carries the full architecture with the multi-register parts stubbed, so it is the clearest public description of OpenPOS's shape.

- **Cashier = an existing WP user with a boolean user meta.** No custom role or capability: users in `array('administrator','shop_manager')` (filter `op_allow_user_roles`) carrying user meta `_op_allow_pos = 1` (`includes/front/Front.php:487-506`), attached to a register via a `_op_cashiers` meta array (`lib/class-op-register.php:5-7`).
- **Register = `_op_register` CPT; outlet = a "warehouse".** Lite hardcodes one register (`lib/class-op-register.php:26-42`) but names the premium meta keys `_op_cashiers` and `_op_warehouse`; receipts address both by shortcode `[op_register field="name"]` / `[op_warehouse field="…"]`.
- **The session is a JSON file on disk.** `OP_Session` writes each till session to `wp-content/uploads/openpos/sessions/<id>` via `put_contents( …, json_encode( $data ), '777' )`, with a sibling `clock/` directory for clock-in/out; ids are `'op-' . time() . '-' . session_id()` off PHP native sessions (`lib/class-op-session.php:24-72`). That file carries `login_cashdrawer_id`, `login_warehouse_id` and `cash_drawers` into everything else.
- **Cash in/out is an `op_transaction` CPT; the running float is a `wp_option`.** Each movement is a post with meta `_in_amount`, `_out_amount`, `_created_at`, `_user_id`, `_store_id`, `_transaction_id`, `_payment_code`, `_payment_name`, `_payment_ref`, `_transaction_details`, `_pos_transaction_cashdrawer`, `_pos_transaction_warehouse` (`includes/front/Front.php:881-957`). The balance is **not derived from that ledger** — it is `get_option( '_pos_cash_balance_' . $register_id )` mutated read-add-write (`lib/class-op-register.php:44-66`), with an admin *reset balance* AJAX action to repair the drift (`includes/admin/Admin.php:65`).
- **The Z report is a snapshot post.** On logout `OP_Report::add_z_report()` inserts an `op_z_report` post titled `"<cashier>@<register>"` with the whole report JSON in `post_content` plus meta `login_time`, `logout_time`, `login_cashdrawer_id`, `login_warehouse_id`, `session_id`, `open_balance`, `close_balance`, `sale_total`, `custom_transaction_total`, `item_discount_total`, `cart_discount_total`, `tax` (`lib/class-op-report.php:17-91`), queried later by `meta_query` on the two timestamps. **Every figure is device-computed and merely recorded**, and in Lite `op_z_report` is never passed to `register_post_type` at all — only `op_transaction` is (`includes/admin/Admin.php:1433-1460`).
- **Attribution, all through `update_post_meta()`**: `_op_order` (the entire POS order as JSON), `_op_order_source='openpos'`, `_op_sale_by_person_id`, `_op_sale_by_cashier_id`, `_op_payment_methods`, `_pos_order_warehouse`, `_pos_order_cashdrawer`, `_op_sale_by_store_id` (`includes/front/Front.php:2809-2825`). No `created_via`, no `declare_compatibility` — **under HPOS every one of those keys lands in `postmeta`, where WooCommerce will not look for it.**
- **No REST API.** The till protocol is `admin-ajax.php`, registered on `wp_ajax_openpos` **and `wp_ajax_nopriv_openpos`** (`includes/front/Front.php:25-26`) — the app authenticates against OpenPOS's own file-backed session rather than WordPress.

### wePOS 2.0.1 (weDevs) — the counter-example: no session model in either tier

`github.com/weDevs/wepos` 404s; the docs redirect to <https://dokan.co/docs/wepos/getting-started/>, last touched 2023 and stale against the 2.0 rebuild.

- **The till gate is `access_wepos`** — `wepos_user_can_access_pos()` is exactly `return user_can( $user_id, 'access_wepos' )` (`includes/functions.php:407-427`), passed through by `map_meta_cap` for `manage_options`/`manage_woocommerce`. The `cashier` **role is never created by free**: the installer calls `get_role()` and `continue`s on null, so `'cashier' => array( 'access_wepos', 'wepos_page_view_pos' )` is a no-op until Pro creates it (`includes/Installer.php:162-170,222-226`).
- **Outlet and counter are Pro; the register identity lives in the browser.** Free carries the seams — options keyed `wepos_outlet_settings_{$outlet_id}` and a query against the Pro junction table `{prefix}wepos_cashier_outlet` wrapped in `$wpdb->suppress_errors(true)` with the comment "Suppress warnings when the pro junction table doesn't exist on wePOS-only installs" (`includes/functions.php:373-402`) — but the React app reads `localStorage["wepos_outlet"]` and `localStorage["wepos_counter"]`. **Nothing on the server binds a register to a device.**
- **No session, drawer, float or Z report in either tier.** Zero hits for `drawer`, `float_amount`, `opening_balance`, `open_register`, `close_register`, `z-report` or `end of day` across `includes/`, `build/`, `assets/js/` and `readme.txt`; the pricing page lists none. Cash is per-order only: gateway `wepos_cash`, tendered/change stamped on the order and never aggregated.
- **Attribution is set client-side.** The bundle whitelists `_wepos_is_pos_order`, `_wepos_tax_based_on`, `_wepos_cash_tendered_amount`, `_wepos_cash_change_amount`, `_wepos_cashier_id`, `_wepos_counter_id`, `_wepos_outlet_id`, posts them as `meta_data` on order create and **drops empty values** — so on free only `_wepos_cashier_id` survives, sourced from `window.wepos.current_user_id`. Server-side, `woocommerce_new_order` sets `$order->set_created_via( 'wepos' )` when `_wepos_is_pos_order` is present (`includes/Common.php:60,190-200`), and a custom status `wc-pos-open` holds parked sales. WooCommerce exposure is one "Is POS" order-list column keyed on `get_created_via() === 'wepos'`; no Analytics integration. HPOS declared (`wepos.php:136-138`).
- **REST + offline.** `wepos/v1`, cookie-nonce auth, routes for products, customers, payment gateways (`GET /payment/gateways` is `'permission_callback' => '__return_true'`), taxes, coupons, settings; **free creates orders straight through `wc/v3/orders`**, `wepos/v1/orders` being Pro (`includes/REST/Manager.php:24-31`). **Offline does not exist** — no IndexedDB, Service Worker, Workbox, localForage, PouchDB or `navigator.onLine` in any bundle.
## 3. WooCommerce facts the models run into

Citations are `path:line` against WooCommerce **10.4.3** (`/Users/kilbot/.wp-env/wp-env-woocommerce-pos-0e0eb911/woocommerce/`, `woocommerce.php:6`).

**Analytics has no cashier, register or channel dimension, and cannot grow one from meta.** `wc_order_stats` is `order_id, parent_id, date_created, date_created_gmt, date_paid, date_completed, num_items_sold, total_sales, tax_total, shipping_total, net_total, returning_customer, status, customer_id` (+ optional `fulfillment_status`) — nothing else (`includes/class-wc-install.php:1254-1278`). No plugin can add a `GROUP BY cashier` to Analytics by writing order meta; the only supported seam is the dynamic clause filter `woocommerce_analytics_clauses_{$type}` / `…_{$type}_{$context}` (`src/Admin/API/Reports/SqlQuery.php:115-121`), which lets a plugin bolt a JOIN/WHERE/SELECT onto the report SQL. **FooSales is the only surveyed plugin that uses it** (§2).

**`created_via` is the one channel field core actually indexes and exposes.** Under HPOS it is a real column, `created_via varchar(100) NULL` on `wc_orders` (`src/Internal/DataStores/Orders/OrdersTableDataStore.php:3266`, mapped at `:454-456`); under the CPT store it is the `_created_via` meta (`:100`). REST v3 both **writes** it (`$object->set_created_via( … ?: 'rest-api' )`, `includes/rest-api/Controllers/Version3/class-wc-rest-orders-controller.php:281`) and **filters on it** (`created_via` query arg, `:360-366`). It is still absent from `wc_order_stats`, so it segments the orders *list* and REST queries, not Analytics.

**HPOS splits meta writes in two.** An order's meta under HPOS lives in `wc_orders_meta`, reached only through `$order->update_meta_data()` / `$order->save()`. A plugin that calls `update_post_meta( $order_id, … )` writes a row into `postmeta` that HPOS-mode WooCommerce never reads — the value is not lost, it is simply invisible to `$order->get_meta()`, to the REST API and to the order list. This is not a theoretical hazard: OpenPOS stamps every one of its cashier/register/warehouse keys that way (§2), and FooSales's own Analytics JOIN has to branch on `OrderUtil::custom_orders_table_usage_is_enabled()` to pick `wc_orders_meta` vs `postmeta` (`fs/foosales/admin/apps/wc_analytics/class-foosales-analytics.php:120-127`).

## 4. Best of everything

### What every plugin converged on (adopt)

1. **The cashier is a WordPress user. All seven.** Not one models a cashier as a CPT or a table row. They differ only in how the till is *gated*: a dedicated role (FooSales `foosales_cashier`, YITH "Cashier"/"Manager", Jovvie `cashier`/`kiosk`, Actuality Register clerk, wePOS Pro `cashier`), a custom capability on existing roles (wePOS `access_wepos`, FooSales `publish_foosales`, Oliver's nine `oliver_pos_*`), or a boolean user meta (OpenPOS `_op_allow_pos`). The capability is the durable part; the role is a convenience for granting it.
2. **Opening a drawer is a separate permission from using the till.** Jovvie gates POS entry on `access_woocommerce_pos` but cash on `cash_management`, which a plain `cashier` does not have; Oliver has `oliver_pos_open_drawer` and `oliver_pos_close_shift` as distinct caps; Actuality has per-user Discounting and Tendering flags. Every product that thought about cash split it out.
3. **Fine-grained till permissions live *beside* WP capabilities, not inside them.** Oliver keeps nine real caps for the coarse gates and ~120 booleans plus numeric limits (`discount_max_percentage`) in one `oliver_pos_roles` option; YITH keeps a per-user `posCaps` map. Nobody registers 120 WordPress capabilities.
4. **Where there is more than one location, the register belongs to an outlet and the outlet owns the hardware and tax settings.** Oliver (outlet CPT → stations table), YITH (store CPT → register CPT), Actuality (Outlet → Register), OpenPOS (warehouse → `_op_register`) and wePOS Pro (outlet → counter) all use two levels, and in all of them the per-*register* settings are display and permission concerns — visible cashiers, payment methods, receipt template — while address, tax and terminal hang off the outlet. Jovvie is the sole exception and its flat station model is a known limitation, not a design.
5. **Attribution is order meta plus the plugin's own metabox and orders-list filter.** Every product stamps a POS flag, a cashier id and (where they exist) store/register ids as order meta, then renders them itself. Nobody puts a cashier in a custom order type or a child order.
6. **The close report is a Z, never an X, and closing is never enforced.** No product ships a mid-shift X read (Jovvie's `get_closeout` is the closest, and it is a live query rather than a printed read). In Jovvie, YITH, OpenPOS and Oliver an unclosed session simply stays open; not one blocks a sale because the previous session was never closed.
7. **Offline, where it exists, covers orders and nothing else.** FooSales and Oliver queue orders on the device and replay them; neither queues a session open, a cash movement or a close. YITH, wePOS and Actuality have no offline at all, and Jovvie's readme concedes the app "needs an internet connection".

### The storage fork, and what each choice costs

**Custom table (Jovvie `pos_till_sessions` + `pos_till_events`, Oliver `oliver_cash_ledger`, YITH `yith_pos_register_sessions`).** The only shape that supports a real cash ledger: append-only rows, a `running_total`/`running_balance` per row, a void pointer (`voided_by_event_id`, `voided_at`) rather than a delete, and a closed set of event types. The costs are the usual ones — no `WP_Query`, invisible to tools that only understand posts, your own schema upgrades. Three products pay them: **the ledger is the one POS entity where append-only row semantics matter more than WordPress-native queryability.**

**CPT (Oliver `oliver_shift`, OpenPOS `op_transaction` + `op_z_report`).** Cheap: free admin list tables, meta queries, REST from `register_meta`. But a session becomes a dozen meta rows, so "sum cash movements for this register today" is a `meta_query` join per key — and Oliver's dual decimal-and-`_cents` writes double that. A per-movement CPT also invites OpenPOS's mistake: a post per movement whose sum is *not* the balance the plugin reads.

**Options and files (OpenPOS `_pos_cash_balance_{id}` and 777 JSON session files; wePOS `localStorage`).** This is where the model stops being auditable. OpenPOS's running float is a `wp_option` mutated read-add-write, so two concurrent movements lose one — and the plugin ships a *reset balance* button because it drifts. Its sessions are files under `wp-content/uploads` at mode 777: outside the database, outside database backups, and readable by anyone who can guess `op-<timestamp>-<php-session-id>`. wePOS keeps the register identity in `localStorage`, so clearing site data silently un-assigns the till. **A balance must be derived from a ledger, and a session must be a database row.**

### Consequences for Analytics, HPOS and REST

- **Nothing written as order meta will ever appear in WooCommerce Analytics on its own.** `wc_order_stats` has no meta, channel or cashier column (§3), so every product ships its own reporting layer and none can answer "sales by cashier" from Analytics unmodified. **Two show the supported route** — FooSales via the `woocommerce_analytics_clauses_{join,where,select}_*` filters with a JOIN branching on `OrderUtil::custom_orders_table_usage_is_enabled()`, and Jovvie via `woocommerce_analytics_*_query_args`; Actuality's docs claim Register and Outlet advanced filters in Analytics > Orders but publish no mechanism. Note the realistic ceiling: FooSales uses its three filters for a two-value POS/online segment, because each further dimension is another JOIN against a one-row-per-key meta table. **A channel segment belongs in Analytics; a cashier or register breakdown belongs in your own report.**
- **`created_via` is the one channel field core indexes and exposes, and most of the field ignores it.** It is a real column under HPOS, `_created_via` meta under the CPT store, and is both written and *filtered* by `wc/v3/orders` (§3). Only wePOS (`'wepos'`) and Jovvie (`'pos-rest-api'`) set it. FooSales, Oliver, OpenPOS and (unverified) YITH leave it and then re-implement POS-vs-online filtering on a private meta key — FooSales with three Analytics filters plus an HPOS branch, YITH with an orders-list filter, Oliver with a whole report tab. **Stamping `created_via` is nearly free and buys the orders list, REST queries and every third-party tool that reads it.**
- **HPOS is a hard fork in how order meta must be written.** `$order->update_meta_data()` + `save()` is HPOS-safe; `update_post_meta( $order_id, … )` is not — the row lands in `postmeta` and HPOS-mode WooCommerce never reads it. FooSales, wePOS, Oliver and Jovvie use the CRUD API and Jovvie annotates `_pos_user` in-source as "the HPOS-safe source of truth"; **OpenPOS writes ten order keys with `update_post_meta()` and declares nothing**, so on an HPOS store its cashier, register and warehouse attribution silently detaches. YITH declared HPOS in 2.11.0 and still needed dashboard and report fixes in three later releases — declaring it is the easy half.
- **Meta-key namespacing is not decorative.** Jovvie writes the operator to **`_pos_user`** — byte-for-byte the key WCPOS uses for the same thing. Two POS plugins on one store would silently overwrite each other's cashier attribution, and neither would report an error.
- **REST auth is the weakest link in the field.** Only Oliver and Jovvie do something defensible: Oliver with three prioritised authenticators and pairing that mints a real WooCommerce key bound to a `device_uuid` unique index, Jovvie with a JWT verified against its cloud and mapped to a WP user. FooSales sends the user's **plaintext username and password in custom headers on every request** and widens CORS to allow it. OpenPOS registers its till endpoint on `wp_ajax_nopriv_` and authenticates against its own file-backed session. wePOS leaves `GET /payment/gateways` on `__return_true`. Actuality documents no auth model at all.
- **Sessions are conspicuously absent from REST.** YITH's session namespace is entirely GET — opening, adding cash and closing all go through `admin-ajax.php`. OpenPOS has no REST. Actuality publishes none. Only Oliver (`POST /shift-report/open`, `/shift-report`, `/shift-report/ledger`) and Jovvie (`/wc-pos/cash/*`) expose sessions as first-class routes, which is also why they are the only two where a native app, rather than a same-origin web view, could drive one.

### Mistakes to avoid, with the product that made each

1. **Storing the balance instead of deriving it.** OpenPOS's `_pos_cash_balance_{register_id}` option, mutated read-add-write, sitting next to an `op_transaction` CPT that already records every movement. Jovvie's `running_total` per event and Oliver's `running_balance` per ledger row are the same idea done correctly.
2. **Trusting the device's arithmetic.** Oliver's `handle_close` records `_expected_cash`, `_cash_sales` and `_total_sales` exactly as the till posted them; OpenPOS's Z report is entirely device-computed. Jovvie is the counter-example: cash payments and refunds emit their own events **server-side** off `woocommerce_rest_insert_shop_order_object` and `woocommerce_refund_created`, idempotent by order id, so the expected figure is the store's, not the client's. If the number is meant to be evidence, the server has to derive it.
3. **A close screen that cannot disagree with the till.** YITH's close is a note and a CSV download; it reports cash-in-hand but never asks what is actually in the drawer, so no variance can exist. Actuality's documented close is a float, free-form Add/Remove Cash and a denomination calculator with no published counted-cash field. Only Jovvie and Oliver persist a counted amount and a computed variance — and only Oliver adds a threshold and a mandatory reason (`_variance_threshold`, `_require_note_on_variance`).
4. **`update_post_meta()` on an order.** OpenPOS, on every POS key it writes.
5. **Client-side capability checks and client-built attribution.** YITH's `posCaps` map is consulted in the JS bundle; wePOS builds the order's whole `meta_data` — cashier id included — in the browser and posts it to `wc/v3/orders`, so the cashier on a wePOS order is whatever the client said. Attribution written by the client is not an audit trail. Jovvie's PIN path is the corrective: a hashed PIN, a rate limit, and a server-side transient proof attached to the order.
6. **Putting the register in the browser.** wePOS's `localStorage["wepos_counter"]`; Actuality's "take over an already opened register" force-logout. Oliver's `UNIQUE KEY user_device (user_id, device_uuid)` is what a bound register looks like.
7. **Filtering empty values out of the attribution payload.** wePOS drops `_wepos_counter_id` and `_wepos_outlet_id` when empty, so the *shape* of a POS order changes silently with the licence tier.
8. **Re-implementing the channel flag you were given.** Five of seven ignore `created_via` and build a private `_*_order_source` meta plus the filtering machinery to go with it.
9. **Letting a report exist that nothing can list.** OpenPOS's `op_z_report` posts are inserted by a post type the Lite build never registers.
10. **Mixing currencies in one drawer.** Jovvie is the only product that scopes a session to `station_id + currency_code` and enforces one live session per pair. Everywhere else a multi-currency store has one undifferentiated float.

## 5. Where WCPOS sits

WCPOS today is on the majority side of every convergent choice and absent from the divergent one. Its
`cashier` role gated by `access_woocommerce_pos` (`includes/Activator.php:486-541`) is the same
capability-plus-role shape as FooSales and wePOS Pro; the Pro store CPT is the same outlet level
Oliver, YITH and OpenPOS all have; `_pos_user` / `_pos_store` order audit meta rendered in an order
metabox and editable there (`includes/Admin/Orders/Single_Order.php:80-121`) is exactly the pattern
all seven share. Two things already put it ahead of most of the field: it sets
`created_via = 'woocommerce-pos'` (`includes/Admin/Menu.php:598`, `includes/API/V1/Templates_Controller.php:902`)
and detects POS orders from it (`includes/wcpos-functions.php:433-435`), where five of seven products
built a private `_*_order_source` meta instead; and `wcpos/v1/cashier/{id}` refuses any id but the
caller's own (`includes/API/V1/Cashier.php:238-271`), where YITH and OpenPOS check the equivalent
permissions in the client bundle. One thing to fix regardless: **Jovvie writes `_pos_user` for the same purpose**, so the two plugins
collide on a live store. The gap is the session — WCPOS has no register-session entity, so no opening
float, no cash movement log, no close and no Z report. The survey says the shape of that gap is
settled: an append-only event ledger in a custom table with a closed event vocabulary and a void
pointer, a session row scoped to register *and* currency, a counted-cash field so a variance can
exist at all, and expected figures the server derives from its own orders rather than accepts from
the till.
