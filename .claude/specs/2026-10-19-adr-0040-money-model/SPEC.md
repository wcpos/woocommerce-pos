# Spec: ADR 0040 on the server — the money model without an epoch

**Date:** 2026-10-19 · **Lane:** `next` · **Decision:** `docs/adr/0040-server-derives-paid-no-money-epoch.md` (accepted, #2332) · **Handoff:** `.claude/handoffs/2026-10-19-adr-0040-money-model/HANDOFF.md` (D1–D6 settled by Paul, not re-asked here) · **Vocabulary:** `GLOSSARY.md` · **Stakes:** High (checkout money, stock) · **Ground truth:** every claim below was read from `origin/next` at `81499e59` on 2026-10-19; where the handoff's table was off, the correction is named.

This spec covers the whole design the handoff describes, PR by PR, and names the pinning test for every rule. PR 1 (the push lane, merged as #2349) and PR 2 (the ledger) are specified to implementation depth; PRs 3–5 are specified to the depth the ADR and handoff fix them, so the PR 1 shapes (key list, lock, error codes) are built once and reused.

## 0. Ground-truth corrections to the handoff

## 1. Vocabulary used below

**Server-owned key** — a document key the push lane drops before the write (ADR rule 2). **Money-sensitive push** — an update whose payload names lines, fees, shipping, coupons, `currency`, `status`, `customer_id`, or a cart restart (`date_created_gmt`). **Open status** — `pos-open`, `pos-partial`, `pending`, `on-hold` (editable after §3.6). **In motion** — a `pending` or `authorized` row, a `sent` gateway attempt, a `pending` refund allocation. **Locked read** — `wc_get_order()` taken after `Order_Lock` was acquired for the push.

### 3.5 The order lock around compare and write (rule 6b)

`Null_Writer::with_write_lock( int $id, array $payload, callable $work )` returns `$work()`. `Order_Writer::with_write_lock()` acquires `Order_Lock::instance()` when `self::is_money_sensitive( $payload )` (any of `line_items`, `fee_lines`, `shipping_lines`, `coupon_lines`, `currency`, `status`, `customer_id`, `date_created_gmt` present), answers `WP_Error( 'woo_rxdb_sync_record_locked', …, 409 )` when it cannot, runs `$work()` and releases in `finally`. `Write_Controller::apply_update()` wraps everything from the current read (`document_for()`) through the revision compare, the context factory (the pre-read), `forward()` and `after_update()` in `$writer->with_write_lock( $id, $m['payload'], … )`. The `Mutation_Store` record lock is already held when this runs, so the nesting order is the one `forward()` used. A push that is not money-sensitive (`customer_note`, billing, `meta_data` only) holds no order lock, as today. `forward()`'s own restart lock goes (the outer lock covers a restart, which is money-sensitive by `date_created_gmt`); `cart_restart_gmt()` and the pre-insert re-decision stay, because the lock is the serialisation and the re-decision is the rule.

### 3.6 Editable statuses and the `reopen_required` gate (rule 4, D3)

**`Orders.php` registers `wc_order_is_editable`** (same priority 10) returning `true` for `pos-open` and `pos-partial`; `Admin\Orders\Single_Order` drops its copy. Reason: ADR rule 2 calls both POS statuses open; D4 makes `pos-partial` derived, so a layaway line edit cannot go through a status flip to `pos-open` (the next money command would flip it straight back and the document would lie in between); `is_editable()` has to answer the same on every request, not only in wp-admin. Pin in `tests/includes/Test_Orders.php`: `is_editable()` true for `pos-open`, `pos-partial`, `pending`, `on-hold` and false for `processing`, `completed`, `cancelled`, `refunded`, `failed` on a plain `wc_get_order()` outside admin.

**The gate** runs in `prepare_order_update_after_read()` on the locked read. `Order_Write_Payload::lines_changed( $order, array $forwarded ): bool` (new, public, beside `for_update()` because it reads the forwarded shape that method produces) answers true when any of `line_items`, `fee_lines`, `shipping_lines`, `coupon_lines` is present and contains: an entry without a numeric `id` (a new line); an entry whose `id` is not on the order; a wc/v3 removal (`item_is_null()` shape — `product_id`/`method_id`/`name`/`code` null — or `quantity` 0); or an entry whose posted money field differs from the stored item (`quantity`, `subtotal`, `total`, `product_id`, `variation_id` for lines; `total`, `tax_class`, `name` for fees; `total`, `method_id` for shipping; `code` for coupons; decimals compared through `wc_format_decimal()` at store precision). `tax_lines` is not read (wc/v3 ignores it). A full-document push whose lines equal storage is **not** a line change, so a note or address edit on a paid order still lands.

When `lines_changed()` is true and `! $order->is_editable()` on the locked read, the push is refused with `reopen_required` (422, `data.status` = current status) **unless** the payload's `status` is in `PUSHABLE_STATUSES` and editable (`pos-open`, `pending`, `on-hold`): then D3 applies — the money-in-motion check of §3.8 runs first, then the status, lines and stock deltas go through as one write. `cancelled` in the payload never unlocks lines.

Pins:
- `test_line_change_on_a_processing_order_is_refused_reopen_required` — quantity change → 422 `reopen_required`; item quantity and `_reduced_stock` unchanged in storage; status unchanged. Data provider over `processing`, `completed`, `cancelled`, `refunded`, `failed`.
- `test_full_document_with_unchanged_lines_on_a_paid_order_applies_the_note` — the order's own serialized document plus `customer_note` → 200; note stored.
- `test_line_change_on_an_on_hold_order_is_applied` — core-editable status, no reopen needed.
- `test_reopen_and_line_change_in_one_push_is_one_write` (D3) — paid `processing` order with one captured cash row, payload `status: pos-open` + quantity change → 200; storage status `pos-open`, quantity applied, the row still present and unchanged (`read_meta()` byte-equal), `date_paid` unchanged, exactly one reopen order note.

### 3.7 Stock deltas on a reopened order (rule 4b)

When the locked pre-read says `$order->get_data_store()->get_stock_reduced( $id )` is true and the forward is an update, `forward_with_order_lifecycle()` adds two hooks scoped to the intent's subject (same `is_subject()` guard as the provenance filter): on `woocommerce_rest_pre_insert_shop_order_object` (priority 20, after the intent at 1 and the stock validator at 10) every stored `line_item` whose id is no longer on the object about to be saved gets `wc_maybe_adjust_line_item_product_stock( $stored_item, 0 )` (restores its reduction while the item row still exists); on `woocommerce_rest_insert_shop_order_object` every `line_item` on the saved order gets `wc_maybe_adjust_line_item_product_stock( $item )` (a new line reduces in full, a changed quantity by the difference, an unchanged line is a no-op because `_reduced_stock` already matches). Each change adds wc/v3's own "Adjusted stock: name (from→to)" note. `require_once WC_ABSPATH . 'includes/admin/wc-admin-functions.php'` exactly as wc/v3 does. On an `on-hold` order wc/v3 has already adjusted set items; the post-save pass then diffs to zero, so nothing double-counts. An order whose stock was never reduced (an unpaid `pos-open` cart) gets no hook: its stock moves at `payment_complete()`.

Pins (product managing stock, qty 10; paid `processing` order with 2 units → stock 8, `_reduced_stock` 2; reopened in the same push with `status: pos-open`; assert through a fresh `wc_get_product()->get_stock_quantity()` and the line's `_reduced_stock`):

- `test_removing_a_line_from_a_reopened_paid_order_restores_its_stock` — 8 → 10.
- `test_changing_quantity_on_a_reopened_paid_order_moves_stock_by_the_difference` — 2 → 3: 8 → 7; then 3 → 1 in a second push: 7 → 9.
- `test_line_change_on_an_unpaid_open_cart_leaves_stock_alone` — `pos-open`, stock never reduced → 10 stays 10.

### 3.8 Money in motion refuses a reopen or a cancel (rule 3)

In `prepare_order_update_after_read()` on the locked read, when the payload's `status` moves the order **out of a non-editable status into an editable one** (reopen) **or into `cancelled` from any status**, read `Ledger::instance()->read( $order )`, `Gateway_Submission::read_attempts( $order )` and `read_stamp( $order )`: a row `pending` or `authorized`, an attempt `sent`, a stamp present, or a refund allocation (`$row['refunds'][*]['status']`) `pending` → `WP_Error( 'wcpos_money_in_motion', …, array( 'status' => 422, 'payment_id' => …, 'attempt_id' => … ) )`, nothing written. Captured, failed and voided rows never block; nothing is archived or re-stamped; a reopen writes no completion entry (PR 2 owns the history) and leaves `date_paid`, `payment_method` and `transaction_id` as they are. The cancel case is this spec's extension of the handoff's rule-3 scope: the ADR calls these "locks on money in motion, not money rules", and a cancel with a card leg still pending would otherwise let the provider land money on a cancelled order; it is listed in §7 for Paul to strike if he disagrees.

Pins (seed rows through `Ledger::save( $order, $rows, false )`; attempts through the order's `_wcpos_gateway_attempts` meta the way `Test_Gateway_Submission` does):
- `test_reopen_with_a_pending_row_is_refused_money_in_motion` — `processing` + pending card row + `status: pos-open` → 422 `wcpos_money_in_motion`, `payment_id` named, status unchanged.
- `test_reopen_with_an_authorized_row_is_refused` — same with `authorized`.
- `test_reopen_with_a_sent_attempt_is_refused` — history `{attempt: 'sent'}`, `attempt_id` named.
- `test_reopen_with_a_pending_refund_allocation_is_refused` — captured row carrying one `pending` refund.
- `test_reopen_of_a_cancelled_order_with_a_standing_authorization_is_refused` — the handoff's pinning case.
- `test_reopen_of_a_paid_sale_with_captured_rows_is_accepted_with_rows_and_balance_unchanged` — `processing`, two captured rows covering the total, `status: pos-open` → 200; `read_meta( '_wcpos_payments' )` byte-equal; `Ledger::summary()` `paid`/`balance` unchanged; `date_paid` unchanged; one reopen note.
- `test_cancel_with_a_pending_row_is_refused_money_in_motion` — `pos-open` + pending row + `status: cancelled` → 422; `test_cancel_with_only_captured_rows_is_accepted` → 200 `cancelled`.

### 3.9 Currency is locked once money exists (rule 6b)

On the locked read, when the payload's `currency` is set and differs from `$order->get_currency()`, and the order has any ledger row (any status), any refund allocation, any attempt in history or a stamp → `WP_Error( 'wcpos_currency_locked', …, 422 )`, nothing written. There is no conversion protocol; a 100 USD row must not cover a 100 EUR total.

### 4.1 Captured rows alone count (D6, rule 1a)

### 4.2 Signed balance

`Ledger::signed_balance( WC_Order $order, array $rows ): int` (public, minor units) = total − Σ captured rows + Σ `succeeded` allocations over every row. `balance()` returns `max( 0, signed )`, keeping its legacy fallback (no rows and `is_paid()`/`date_paid` → 0). `summary()` gains `refund_due` = `max( 0, −signed )` and `refund_pending` = Σ `pending` allocations, never added to the balance. `record()`/`intent()`/`submit()` keep comparing against `balance()`. **`derive()` completes on the same signed balance**: its `$total > 0 && $paid >= $total` test becomes `$total > 0 && $this->signed_balance( $order, $rows ) <= 0`, so a reopened sale that was partly refunded (100.00 captured, 20.00 refunded, total still 100.00) is not completed by a 10.00 cash `record` (signed balance 10.00) — the gross-captured comparison would have. The `pos-partial` projection keeps reading Σ captured > 0. `Ledger::save()`'s attempt-paid marking keeps the gross comparison (it answers "did this send's row cover the order", not "is the order paid").

### 4.4 The completion stamp (rule 1c)

New `includes/Payments/Contract/Completion_Stamp.php`, armed from `Service_Groups` beside the other payment hooks. Constants `META_KEY = '_wcpos_completions'`, `COMPLETED_AT_META_KEY = '_wcpos_completed_at'`; `Pos_Order_Audit::SERVER_MONEY_META_KEYS` references them (already in the list as literals).

**"Paid" for the stamp** is `get_date_paid( 'edit' )` set **and** the status in the **completed set**: `wc_get_is_paid_statuses()` plus the per-gateway POS status for the order's method (`apply_filters( 'woocommerce_payment_complete_order_status', 'processing', $id, $order )`, which `Orders::payment_complete_order_status()` resolves for a POS order; a merchant may store a non-core status there and `payment_complete()` lands on it with `date_paid` set). An unpaid status write under `Paid_Date_Suppression` has no `date_paid` and is never a completion. The **open set** is `pos-open`, `pos-partial`, `pending`, `on-hold`, `failed`, `cancelled` for the reopen observer below.

**Entry points** (three, all converging on `stamp()`; `woocommerce_payment_complete` does **not** fire when `payment_complete()` is called on an order already in a paid status — WooCommerce fires `woocommerce_payment_complete_order_status_{status}` instead — so no entry point relies on a second `payment_complete()`):
- `woocommerce_order_status_changed` at priority **5** (before `Gateway_Submission`'s stamp clear at 10 and `Webview_Passthrough` at 10). Two jobs. (a) **Completion**: when `$to` is in the completed set and `$from` is not, memoise the awaiting-customer stamp's `provenance` (if any) for the order, then `stamp( $order )`. Inside `payment_complete()` this fires first (the status is persisted, `date_paid` with it), so the entry exists before every `woocommerce_payment_complete` listener runs; for a gateway that lands a paid status without `payment_complete()` it is the only signal. (b) **Reopen**: when `$to` is in the open set and `$from` is not, or `$from` is in the completed set (a completion into a configured `on-hold` status leaves from an open status), mark the latest entry `reopened_at_gmt = now` if it is unmarked, and, when the history is empty and `date_paid` is set, synthesise the legacy entry 1 first (below) and mark it. Both jobs write through the same locked read-modify-write.
- `woocommerce_payment_complete` at priority **15** (after `Webview_Passthrough::on_payment_complete()` at 10 has minted the captured row for an asynchronous order-pay completion — a gateway whose webhook calls `payment_complete()` in a later request, with no window, no provenance and no row yet when the status observer ran): `stamp( wc_get_order( $id ) )`, which now finds the captured row as its origin. A no-op when the status observer already stamped (the duplicate rule below).
- `Completion_Stamp::with_provenance( array $provenance, callable $work )`: the request context the money commands set (not an entry point itself; `stamp()` reads it).

**`stamp( WC_Order $order )`** runs under `Order_Lock` (reentrant with the route lock; when the lock cannot be taken it logs, notes the order "WCPOS: completion could not be recorded; reconcile manually." and returns — never throws). It writes nothing unless the order is paid (above) **and** the completion has a **register origin**: a provenance context is set (a money command in this request), `Ledger::is_deriving()`, `Gateway_Submission::is_submitting( $id )`, `Webview_Passthrough::is_paying( $id )` **and** `wcpos_is_pos_order( $order )` (the order-pay window is set for every storefront order-pay POST; the POS-origin check is what `mint()` already applies), a memoised attempt provenance for the order, or a captured ledger row on the order. A storefront order paid online meets none and is never stamped. **Duplicate rule** (replaces any request-scoped memo): on the locked read, if the latest entry exists and is not marked `reopened_at_gmt`, the sale is already completed for this cycle and nothing is written — this is what stops two concurrent gateway callbacks that both loaded the reopened order from writing entries 2 and 3, and what makes the priority-15 hook a no-op after the status observer. A new entry is appended only when the history is empty or its latest entry is marked reopened. **Windows:** while `Gateway_Submission::is_submitting( $id )` or `Webview_Passthrough::is_paying( $id )` is open, the tender row is minted only after the status transition (after `process_payment()` returns, or at the passthrough's priority-10 listeners), so the status observer at 5 only memoises and marks reopens there; the stamp is written by a second status-change listener at priority 15, by the `woocommerce_payment_complete` listener at 15, or by `submit()` itself after its mint, and inside a window `stamp()` writes nothing until a captured row exists. Otherwise the entry would carry `payment_ids: []` and the fiscal snapshot no payment (found by the adversarial review). A memoised sent attempt counts as awaiting its row too, and a sent attempt completed by a paid-status write with no `payment_complete()` and no window (the invoice flow: sent from the till, paid by bank transfer, marked paid in wp-admin) has its row minted by the stamp itself through the passthrough (attempt id as row id, `source app`, `capture_mode gateway`, the stamp's method) before the entry is written, so the completion and its document name the tender and the attempt history flips to `paid`. A move between two completed statuses (processing → a configured `on-hold`) marks no reopen.

**Provenance** (`register, session, sale_time, sale_tz, counter`), resolved in this order: the request context set by `with_provenance()`; the memoised stamp provenance (a `submit` completed by a later callback); the write-once till tuple (`_wcpos_register`, `_wcpos_session`, `_wcpos_sale_time`, `_wcpos_sale_tz`, `_wcpos_sale_counter`), which is the fallback for completion 1 and for the order-pay webview. A value that is absent stays null; nothing is invented. The request context is a `provenance` object on the bodies of `record`, `intent`, `capture`, `submit` and `close` (`register_id`, `session_id`, `sale_time`, `sale_tz`, `sale_counter`), validated field by field with `Pos_Order_Audit::is_valid_till_value()` under the matching till key and dropped when invalid, never refused; `Payments_Controller` wraps only those five handlers in `Completion_Stamp::with_provenance( $provenance, $work, $order_id )`; `status`, `void`, `refund` and `cancel` run with no context, so a status poll that completes the order stamps the captured row's register. For `submit`, `Gateway_Submission::submit()` also writes the validated provenance into the awaiting-customer stamp as `provenance` when the outcome is `sent`, so a callback that completes the order in a later request still names the register that sent it.

**The entry** appended to `_wcpos_completions` (JSON list): `{ id: uuid4 minted here, n, at_gmt, sale_time, sale_tz, register, session, counter, total, payment_ids, reopened_at_gmt: null }` where `payment_ids` are the captured row ids at that completion (§4.6 reads them) and `total` is `get_total()`. `_wcpos_completed_at` = `at_gmt`. **Legacy synthesis** (an order completed before this ships: `date_paid` set, history empty): entry 1 is synthesised at the first reopen (job (b) above) or, failing that, at the first later completion — `id` = `digest_source_id( 'sale:' . row id )` when `Fiscal_Record_Store::find_sale( order_id )` has a row, else a uuid4; `legacy: true`; `at_gmt` = the row's `received_at_gmt` or `date_paid`; provenance per field through the chain fiscal row → till tuple → the latest captured row's register and session (so a sale row with a null session does not blank a session the legs carry); `total` = the row's payload total or `get_total()`; **`payment_ids` = the captured row ids on the order at synthesis** (so a pre-deploy cash sale is as non-voidable after reopen as a new one); `reopened_at_gmt` set when synthesised by the reopen job. The new entry is then 2. ### 4.7 Fiscal identity on the completion (the handoff's Fiscal row)

- `Fiscal_Record_Store::record()`: `sale` and `cancellation` key on `source_id`; `late_sale` moves to `source_id` too (the digest of the completion's own sale row, `late_sale:{record id}`), since a second completion landing late must write its own correction rather than replay the first; the others unchanged. `find_sale( int $order_id, ?string $completion_id = null )`: with an id → `( type sale, order_id, source_id )`; null → the latest sale by `order_id` (`find()` takes an order direction; this is the one `DESC` reader). No backfill.
- **The sale writer's trigger is `wcpos_sale_completed( $order, $n )`**, not `woocommerce_payment_complete`: `Fiscal_Record_Writers` subscribes `handle_sale_completed( $order, $n )` in place of `handle_payment_complete()` (which goes), so a gateway that lands a paid status without `payment_complete()` and an asynchronous order-pay completion both reach the writer through the one path the stamp owns, after the entry is persisted. The writer condition is **"has a non-legacy completion entry"** (the `wcpos_is_pos_order()` gate on the sale path goes; an online order finished at a register is a sale at that register).

## 5. PR 3 — command idempotency and revision (rules 5, 6a; `feat/adr-0040-3`)

Ground truth read from `origin/next` at `0ccfe87e` (2026-10-20). ### 5.1 The command envelope

Every body on the route family except the status poll carries two more fields:

| Field | Type | Required on | Missing or invalid |
|---|---|---|---|
| `command_id` | uuid (lower-cased) | `intent`, `capture`, `void`, `refund`, `cancel`, `submit`, `close` | 400 `rest_invalid_param` |
| `revision` | string (`sha256:…`) | the seven above **and** `record` | 428 `wcpos_revision_required` (the push lane's `woo_rxdb_sync_revision_required` is 428 too) |

`record` has no `command_id`: its row id is the command id (ADR rule 5) and its whole body is the fingerprint (stored on the row it creates, refused rows included, after PR review); one sent is ignored. The webview mint is not a route and carries neither. `GET …/payments/{uuid}/status` is a poll, not a command: it takes no `command_id` and no `revision`, and nothing it applies is a till command (the provider's answer is the fact). A `provenance` object (PR 2) stays where it is and is part of the body fingerprint.

**Fingerprint.** `Command_Log::fingerprint( string $kind, string $target, array $body ): string` = `'sha256:' . hash( 'sha256', wp_json_encode( Revision::canonicalize( [ 'kind' => $kind, 'target' => $target, 'body' => $body minus command_id, revision ] ) ) )`: the route (`kind`), what it addresses (`target`: the payment uuid for a row command, the method id for `submit` / `cancel`, `''` for `close`), and the body with sorted keys at every depth and values as sent (a till retries the bytes it sent; `10` and `"10.00"` are different bodies). A command id reused on another route or another row is therefore a different fingerprint, and a 422. For `submit`, `attempt_id` and `values` are in the body and so in the fingerprint; for `refund`, `refund_id` and `amount`; for `intent`, `payment` and `context`; for `capture`, `context`; for `void`, `reason`; for `cancel`, `attempt_id` and `reason`; for `close`, `provenance` alone.

### 5.2 Where an outcome is kept (rule 5)

No new table, no new option. Two maps, both already in `Pos_Order_Audit::SERVER_MONEY_META_KEYS` (§3.3) so a push cannot write them:

- **Row-level** (`intent`, `capture`, `void`, `refund`): `row['commands'][ command_id ] = { fp, kind, ref, at_gmt }` where `ref` is the `refund_id` for a refund and `null` otherwise. `normalize_row()` keeps `commands` as an array (default `array()`); `Ledger::save()` serialises rows through `to_wire()`, so **`to_wire()` is not touched** (a strip there would erase the map from `_wcpos_payments` on the next save); the route layer drops it from answers through `Payments_Controller::wire( array $row )` = `Ledger::to_wire()` minus `commands`, used everywhere the controller returns a row (`payment_response()`, `gateway_item()`, `provider_item()`); `RECORD_INPUT_KEYS` already excludes it so a client cannot seed it. **Never evicted** while the row exists: one entry per distinct command id, no `EVENTS_MAX`-style slice.
- **Order-level** (`submit`, `cancel`, `close`): `_wcpos_commands` = `{ command_id: { fp, kind, ref, outcome, at_gmt } }` where `ref` is the attempt id (`submit`, `cancel`) or the completion id the close produced (`null` when none stood), and `outcome` is the submit's wire outcome (`sent` / `settled` / `recorded`) so the replay survives the attempt history's `ATTEMPTS_CAP` eviction. Never evicted for the order's lifetime; `ATTEMPTS_CAP` stays (the history is a fate index, the map is the command record).

**An entry is written for every command answered 2xx**, in the same save as its effect when it has one, or in a save of its own when the command changed nothing else (a `refund` under a new command id for an already-allocated `refund_id`, a `close` that replays a standing completion, a `submit` or `cancel` answered from the attempt history under a new command id), so a 2xx command id can never be reused with another body. The effect saves: the row transition (`capture`, `void`), the allocation (`refund`), the pre-dispatch row save (`intent`: the entry rides the `pending` row persisted before the provider is asked, so a lost answer still records the command and the retry resumes), the attempt's `sent` save before `process_payment()` (`submit`: removed again by `restore_method()` in the same save that marks a definitely failed attempt `cancelled`, so the entry and the attempt fate never disagree; the attempt stays terminal, as `test_clean_provider_failure_leaves_terminal_attempt` pins, and the same command retried meets the 409 state conflict below, never a second dispatch), the cancel's `update_status()` save (`cancel`: staged with `update_meta_data()` before it), and the completion's own save (`close`: the entry is staged with `ref` null on the order through `Command_Log::remember()` **before** `derive()`, so it rides WooCommerce's completion save; the completion id exists only after `payment_complete()` has run, so `close()` fills `ref` on the fresh re-read it already makes and saves it under `Ledger::saving()`. A crash between the two saves leaves the entry with `ref` null, and its replay names the latest standing completion when `Completion_Stamp::stands()`, the answer `close` gives a standing completion, else `completion: null`; pinned as 5.6 #30). A refusal that changed nothing (400/404 validation, 409 lock, `wcpos_balance_outstanding`, `wcpos_payment_in_flight`, a determinate provider refusal that deleted the intent row, a provider error on capture) **stores nothing**: the retry runs again. A capture refused by the provider still appends its failure events to the row (`record_failure_events()`), which moves the revision, so that retry meets 409 `wcpos_revision_stale` and runs after the till re-reads; that is the ADR's refusal-then-re-read, not a stored outcome. That is the ADR's consequences paragraph applied: no stored failure can poison a later honest retry, and nothing has to be swept. `record`'s refused-row path (`failed` row with `failure_reason`) is already its own stored outcome and is unchanged.

**Lookup is order-wide**: `Command_Log::find( WC_Order $order, array $rows, string $command_id ): ?array` searches every row's map and the order map, whichever route the request came in on; the entry's fingerprint (which names kind and target) decides replay or 422. The URL row of a `capture` is not where the id is looked for; it is only what the fingerprint must name.

**Same id, same fingerprint** replays: `capture`, `void` → `{ payment: row, order, revision }` from the row as it now stands; `refund` → `{ payment: row, revision }`; `cancel` → `{ order, revision }`; `close` → `{ order, completion: { n, id } from the history entry whose id is ref (null when ref is null or the entry is gone), revision }`; `submit` is **called through** to `Gateway_Submission::submit()` after the fingerprint check: the attempt history's fates keep precedence over the stored outcome (`cancelled` / `superseded` → 409 `wcpos_payment_conflict`, `sent` / `settled` / `paid` / recorded row → the replay, as today), and only when the history no longer names the attempt (`ATTEMPTS_CAP` eviction) does `submit()` answer `{ outcome: entry.outcome, payment: row(ref) or null, order }` from the map without dispatching; `record` and `intent` are **called through** (their row-id replay is the stored outcome: `record()` compares the immutable fields, `intent()` resumes a pending leg at the provider or returns the settled row, exactly as today). No provider is called by a replay except the intent resume, which is keyed on the row id at the provider (§4.3 of the hardening spec) and is the designed recovery of a lost handoff.

**Same id, different fingerprint** → 422 `wcpos_command_conflict`, data `{ status: 422, command_id, kind }`, nothing written, no provider call. `record`'s mismatched replay moves from 409 `wcpos_payment_conflict` to the same 422 (data keeps `payment`: the stored row), so one code means one thing across the family (§7 decision 12). `submit`'s `cancelled` / `superseded` refusal keeps 409 `wcpos_payment_conflict`: that is a *state* conflict (the till undid the attempt), not a body conflict.

**Same id in flight** → 409 `wcpos_payment_locked`: the route lock, already pinned per route (`test_every_order_route_obeys_lock`). Nothing is persisted as "in flight" (an in-flight marker that outlives a crashed request is the poison lane the ADR rejects); `intent`'s and `submit`'s pre-dispatch saves are the rule-7 two-save shape, not a marker.

A command id is scoped to its order: the same uuid on two orders is two commands. Within the order there is one namespace, and a recorded row's id is in it (the row id is `record`'s command id): `Command_Log::find()` answers a row whose id is the command id as an entry of kind `record` with `fp` null, so another command reusing a row's id as its `command_id` is the 422 by fingerprint mismatch, and a `record` whose `payment.id` another command already consumed is 422 `wcpos_command_conflict` with no row created (5.6 #28).

### 5.3 Revision (rule 6a)

`Order_Serializer::current_state( int $order_id ): array{ document: array, revision: string }` does the bare read `Order_Writer::document()` does (`dispatched_bare_read( '/wc/v3/orders/' . $id, ['dp' => '6'] )` plus `add_pos_links()`) and hashes it with `canonical_revision()`. `Write_Controller::revision_for()` is untouched; a pin proves the two agree (5.6 #5). It is only ever called under the route lock. **The inner read's failure propagates**: a response with status ≥ 400 (the cashier lacks read permission on the order, the order vanished) is returned as a `WP_Error` carrying that status and code, nothing is written, and no hash of an error body is ever presented as a revision (the push lane does the same at `Write_Controller::apply_update()`).

Order of checks in `Payments_Controller`, inside `with_lock()` after `get_order()` and before any ledger call:

1. Parse `command_id` (400) and `revision` (428) per 5.1; compute the fingerprint.
2. **Replay lookup first** (ADR rule 6): `record` → the row with `payment.id` exists; `intent` → `Command_Log::find()` has the id with the same fingerprint (a **new** command id on an existing row is a fresh command and meets the revision: stale → 409 `wcpos_revision_stale` before the provider is called; current → the row's resume, as today; 5.6 #29); the other five → `Command_Log::find()` has the id anywhere on the order. A hit with the same fingerprint answers per 5.2 and **skips the revision compare** (a retry carries the revision from before its own effect). A hit with another fingerprint is the 422.
3. **Fresh command**: `current_state()`; `revision !== current.revision` → 409 `wcpos_revision_stale`, data `{ status: 409, currentRevision, current: document, order: summary }` (the push lane's conflict shape plus the summary), nothing written.
4. Run the command, passing `$command = [ 'id' => …, 'fp' => … ]` to the ledger or submission (optional trailing parameter, default `array()`: Pro's callers and the webview mint pass none and store nothing).
5. Every 2xx answer, replay included, gains top-level `revision` = `current_state()` computed **in the route wrapper after `Fiscal_Record_Writers::recover()` has run**, still under the lock (recovery may clear `_wcpos_fiscal_pending`, which moves the revision), so the till can chain `record` → `close` without a pull. The status poll returns none.

The hash already covers `meta_data` (`_wcpos_payments`, the index rows, the live-leg key, `_wcpos_commands`, `_wcpos_completions`) and `status` / `date_paid` / `payment_method`, and excludes `date_modified*`, so a money command moves the revision a later push compares against (pinned, 5.6 #5 and #6) and a no-op save does not (5.6 #7). An offline cash row recorded against the revision the till held and replayed after an unrelated server-side edit is a replay by row id: one row (5.6 #16). A fresh offline row carrying a stale revision is refused so the till re-reads and re-sends with the same row id (5.6 #17); the cash is in the drawer either way and the row id is the identity, so the re-send creates one row.

## 6. PR 4 — the refund two-save and the sweeper's lookup (rules 8, 7; `feat/adr-0040-4`)

Ground truth read from `origin/next` at `33943dc8` (2026-10-20). `Ledger::refund()` validates the row (counting status), the refund object (type, parent), the amount and the two caps (row availability, refund amount across rows), then calls the capture-mode handler's `refund( $row, $refund_id, $amount )`, which **calls the provider and appends the allocation to the row it returns** in one step: `Gateway_Handler` runs `$gateway->process_refund()` when the gateway `supports( 'refunds' )` and appends `{id, amount, status: 'succeeded', provider_ref: null}` (a boolean answer carries no reference); `Manual_Handler` appends `succeeded` without a call; `Webview_Handler` runs the gateway the same way; Pro's `Server_Handler::refund()` asks its adapter and appends the adapter's `status` (`succeeded`, `pending` or `failed`) and `provider_ref`. `Ledger::refund()` then applies the handler's row, recomputes `refunded_amount`, adds the command entry (PR 3, `ref` = refund id) and does **one** `replace_and_save()`, after which `woocommerce_pos_refund_allocated` fires (listeners: `Fiscal_Record_Writers::handle_allocation()`, Pro's `Refund_Sweep::allocated()`). So the allocation reaches storage only after the provider has refunded: a save that does not land (a throw inside `$order->save()` is swallowed and logged, memory `wc-order-save-swallows-exceptions`; a lock or DB failure) leaves no allocation, no entry and no trace, and a retry under any command id calls `process_refund()` again. That is the double refund rule 8 forbids and the one Codex finding declined on #2355.

Who calls it: the Free route `POST …/payments/{uuid}/refund` (`Payments_Controller::refund_item()` → `provider_item()`, inside the route lock, with the admitted command); Pro's `Refund_Processor::allocate_refund_locked()` (one `Ledger::refund()` per planned allocation, no command, inside `woocommerce_create_refund` at priority 20, so a **`WP_Error` returned before any leg succeeded becomes a thrown exception and WooCommerce deletes the refund it just created**, and an exception that escapes the hook does the same); Pro's `Order_Pay_Gateway` (one call, no command). `settle_allocation()` already exists for a later provider answer on a `pending` allocation (status, reference, `refunded_amount`, fires the hook on a final answer); `summary.refund_pending` already sums `pending` allocations without adding them to the balance (PR 2); `Order_Writer::money_in_motion()` already refuses a reopen or cancel while an allocation is `pending` (PR 1). A `pending` allocation is therefore a shape the ledger, the summary and the push lane already understand; PR 4 makes every refund pass through it.

### 6.1 The two saves in `Ledger::refund()` (rule 8)

After the existing validation and caps, and before the handler is called:

**Save 1 — reserve.** The row gains the allocation `{ id: refund_id, amount: Money::normalize( $amount ), status: 'pending', provider_ref: null }` and, when the caller has a command, the command entry (`with_command( $row, $command, $refund_id )`, exactly the entry PR 3 stored after the call). `replace_and_save( …, derive: false )` (no money has moved; the projection is unchanged by a reservation). The write is verified by a fresh read of storage (`stored( $order_id, false )`, the read-back PR 3's `command_kept()` uses): the allocation is `pending` for that refund id on that row and, with a command, the entry is present. Both halves are checked: an allocation without its entry, or an entry without its allocation, is a miss. A `Throwable` out of `save()` (its storage read, its persistence check) is a miss too, never an escape. On a miss the save is written once more and read again; a second miss **withdraws** whatever half landed (one verified save; a withdrawal that does not land is logged and noted as in §6.2) and returns `WP_Error( 'woo_rxdb_sync_record_locked', …, [ 'status' => 409 ] )`, the same code the route gives a lock conflict, and **the provider is never called**. It is a returned error, never a thrown one: Pro's `allocate_refund_locked()` runs one `Ledger::refund()` per planned leg inside WooCommerce's deleting `catch`, and an exception on leg B after leg A refunded would delete the whole refund; a `WP_Error` after a succeeded leg is what Pro already records as a failed leg and keeps the refund for.

**The handler call.** `$handler->refund( $row_before_save_1, $refund_id, $amount )` with the row **as it was before the reservation**: every handler appends its own allocation for the refund id, and the handler contract (`Capture_Mode_Handler_Interface::refund()`, Pro's `Server_Handler`, every third-party handler) does not change. The call is wrapped in `try … catch ( \Throwable )`.

**Save 2 — settle.** The handler's row goes through `apply_transition()`, the amount checks and `refunded_amount` exactly as today; the command entry is added; `replace_and_save()` with **derive off** replaces the stored row whole, so the handler's allocation for the refund id (`succeeded`, `failed`, or `pending` with a provider reference for a Pro adapter that answers later) stands where the reservation was. Verified by a fresh read, both halves as at save 1: the stored allocation for the refund id **equals the handler's allocation** (status, `provider_ref` and amount; a status check alone cannot tell a Pro adapter's `pending` with a reference from the reservation's `pending` without one) **and, with a command, the entry is present** (a settle that kept the allocation but lost the entry would let the same id be admitted with another body later). **Derivation is its own save, after the settle has landed**: `derive()` over the rows as read, then one `$order->save()` under `Ledger::saving()`, the sweeper's shape. It must not ride the settle attempt: on a reopened sale with excess captured money a succeeded refund covers the signed balance, and a derive inside a settle attempt that then does not land would have run `payment_complete()` and stamped a completion on an order whose refund is still `pending`, which rule 3 forbids. A derive save that throws or does not land is logged as a warning and left to the next money command or `close` (rule 1 re-derives on every money write); the allocation is settled, so it is never a strand. A `Throwable` out of `save()` is a miss, never an escape (through Pro's hook it would delete the refund after the provider refunded). On a miss the save is written once more; a second miss is a **stranded allocation**, §6.2. When the settle lands, `woocommerce_pos_refund_allocated` fires once, with the handler's row, exactly as today: the hook never fires for the reservation, so `Fiscal_Record_Writers` and Pro's `Refund_Sweep` see what they see now.

**A definite refusal.** The handler returns a `WP_Error` without `indeterminate => true` in its data (`wcpos_provider_error` 502 after `process_refund()` answered `false` or a definite `WP_Error`, `wcpos_payment_method_not_found` 404, `wcpos_capture_mode_unsupported` 501, a Pro adapter's definite refusal), or returns a row whose allocation for the refund id is missing or `failed` (the existing post-call checks answer that with `wcpos_refund_not_allocatable` 400 and store nothing, today and still): no money moved, so the reservation and the command entry are **withdrawn** in one verified save. A post-call check that fails on a row whose allocation for the refund id is `succeeded` or `pending` (a handler that saved more than it was asked, or an invalid transition after the provider answered) is **not** a refusal: the money moved or is in motion, so the reservation stands and the outcome is stranded (§6.2) with the check's error logged; the withdrawal is only for a result that says no money moved (§7.13: a refusal stores nothing, and the same command id retried runs again) and the handler's error is returned as today. A withdrawal that does not land after its one retry is logged (`Logger::log`, error) and noted on the order with its own wording (`WCPOS: refund #%1$d for %2$s did not go through %3$s but its reservation could not be removed; check the payment before retrying.`, the same words whether the handler refused or the reservation itself never landed), and the handler's error is still the answer; the reservation then stands until a human settles it (§7.17).

**An outcome the server cannot know.** The handler returns a `WP_Error` carrying `indeterminate => true` (`Gateway_Handler::refund()` and, through it, `Webview_Handler` today replace the gateway's `WP_Error` with `wcpos_provider_error` and keep only the status: they now copy `indeterminate => true` from the gateway's error data into the data of the error they return, the one code change outside `Ledger`), or **throws** (a gateway's `process_refund()` raising mid-call: the provider may or may not have refunded): the reservation stays `pending`, the order gets the note of §6.2, the error is logged with its message, and `Ledger::refund()` **returns the stored row** (the reservation, not an error): through Pro's hook a `WP_Error` would be thrown and the refund deleted after money may have moved, which is what rule 8 forbids; through the Free route the till is answered 200 `{payment, revision}` (the refund answer's shape, pinned by `test_refund_response_contains_only_payment`) with the `pending` allocation on the payment's `refunds`, the true state (§7.16); `summary.refund_pending` carries its amount on every order summary the till reads next (`close`, the order document, a `capture` or `record` answer).

**Replay and reuse** need no new code: PR 3's `replay()` finds the row entry (stored at save 1, `ref` = refund id) and answers `{payment}` from storage, so a retry of a stranded command answers the `pending` allocation and the provider is not asked; the existing "already allocated" loop at the top of `refund()` (any allocation for the refund id, whatever its status) answers a **new** command id for the same refund with the row and notes the new entry, and the provider is not asked. Pro's callers are unchanged in signature and, on the success path, in behaviour (two saves instead of one; the hook once).

### 6.2 The stranded allocation (rule 8's "marks it for attention")

An allocation is stranded when the provider was asked (or may have been) and storage holds `pending` after the settle's retry: the settle did not land, the handler threw, or the handler's error was indeterminate. Three things happen, in this order, and nothing else:

1. `Logger::log()` at error level, naming the order, the row, the refund id, the amount and the cause (the save that did not land, or the exception's class and message).
2. An order note through `$order->add_order_note()`: `WCPOS: refund #%1$d for %2$s was sent to %3$s; confirm it with the provider before retrying.` (refund id, amount with currency, the row's `method_id`). The note is a comment row, written by its own query, so it survives the order save that did not land.
3. The row is returned as stored, with the `pending` allocation (the route's answer is `{payment, revision}`; the summary is not in a refund answer).

Steps 1 and 2, and the `woocommerce_pos_refund_allocated` action after a landed settle, run inside their own `\Throwable` guard: a note hook (`woocommerce_new_order_note_data`, `woocommerce_order_note_added`), a logger or an allocation listener that throws must not escape `refund()`, because through Pro's hook that exception deletes the refund after the provider refunded. A throw from a listener is logged and swallowed; a throw from the logger itself is swallowed.

What the pending allocation does from then on is what it does already: `summary.refund_pending` carries its amount on every order summary and the balance does not (PR 2's pin `test_summary_reports_a_pending_allocation_as_refund_pending_not_as_balance`); a reopen or cancel on the push lane is refused with `wcpos_money_in_motion` (PR 1's pin); `available_for_refund()` keeps the amount reserved; a replay of the command answers it; a new command for the same refund answers it. No sweeper settles it: `Gateway_Handler` records no provider reference (`process_refund()` answers a boolean), so there is nothing to poll, and `Payments_Sweeper` reads payment legs, not allocations. A human reads the note, confirms at the provider, and a developer settles it with `Ledger::settle_allocation( $order, $row_id, $refund_id, 'succeeded' | 'failed' )` (§7.17). Pro's `pending` allocations with a provider reference keep their own sweep (`Refund_Sweep`), unchanged.

### 6.3 The sweeper's provider lookup (rule 7, verification)

Rule 7's clause "a sweeper resolves a stranded attempt by asking the provider for the client's reference before any retry" was read against `Payments_Sweeper::run()`: a leg older than the threshold is **re-dispatched** through `$handler->intent( $row, [ 'source' => 'sweep', 'reader' => … ] )` only when `Ledger::is_unanswered( $row )` (status `pending` and no provider reference other than `reader`), and the row passed is the stored row, whose `id` is the client's reference the handler's create is idempotent on (Pro's `Server_Handler` recovers a live provider object through that id; the sweeper's own comment says so); a leg with any provider reference is **polled** through `$handler->status()`; `manual` and `webview` legs are never dispatched; an unanswered leg on a closed order is voided through the handler, not blind. Pinned today in `Test_Payments_Sweeper`: `test_sweeper_actionless_pending_is_dispatched_then_polled`, `test_sweeper_pending_with_action_is_not_redispatched`, `test_sweeper_device_row_with_payment_intent_is_polled_not_redispatched`, `test_sweeper_voids_an_unanswered_row_when_the_order_is_closed`, `test_sweeper_indeterminate_intent_leaves_row_untouched`. The first of those already asserts that the re-dispatched intent receives the stored row's `id` and `source` = `sweep` (confirmed in the pre-build review), so rule 7's provider-leg half needs no new pin and PR 4 adds none.

WooCommerce gateway attempts (`submit`, `_wcpos_gateway_attempts`) are the other half of rule 7 and are **not** covered by a lookup: a WooCommerce gateway answers `process_payment()` once and the gateway API has no lookup by reference, so no sweeper can ask. A `sent` attempt is resolved by the gateway's own completion (`payment_complete()` adopts the row and the attempt becomes `paid`), by the till's `cancel`, or by a newer send superseding it; one that none of those reaches blocks reopen (`money_in_motion()` reads `sent`) until a human cancels it, and PR 3's cleanup logs the one case it cannot repair. PR 4 changes nothing here; §7.18 records it.

## 7. Decisions this spec makes that Paul should see (not re-asks of D1–D6)

1. **`pos-partial` is editable** (§3.6), globally, by the same filter that makes `pos-open` editable. Alternative rejected: requiring a reopen to `pos-open` for a layaway line edit, which the next money command would undo.
2. **A push into `cancelled` is refused while money is in motion** (§3.8), the same check as a reopen. Strike it and the cancel passes through as today.
3. **`lines_changed()` compares money fields only** (§3.6): a full-document push whose lines match storage is not a line change. A change to a line's display name alone is invisible to the gate, by design.
4. **The v1 `set_paid` path on `/wcpos/v1/orders` is untouched** (§3.2). It is the frozen data lane; D1 names the push lane. Whether it is stripped in 2.0.0 or dies with v1's deprecation is a question for Paul before PR 5.
5. **Overselling on the ledger path.** After PR 1 the only way a till completes a sale is a money command, and `Stock_Validator` guards none of them (`validate_stock` hooks only wc/v3 pre-insert; `around_paid_create` runs only for an `on-hold` create). Prevent-overselling at the moment of payment is therefore unenforced on `next` today and stays so after PR 1. It is a PR 2 design item (the hold belongs in `record`/`intent` under the order lock, before `derive()`), listed here so it is not lost.
6. **The balance formula counts allocations, not WooCommerce refund objects** (§4.2): Σ `succeeded` allocations on ledger rows. A wp-admin refund that is never allocated to a row does not enter the balance; the adopted tender (§4.5) imports the order's existing refunds as allocations so a reopened online sale starts consistent. Consequence worth seeing: a 100.00 sale paid in full and refunded 20.00 reads `balance 20.00` after a reopen, so closing it unchanged is refused until the returned line is removed or the 20.00 collected. That is the ADR's formula applied as written, and `derive()` now applies it too.
7. **The completion history records the reopen** (§4.4, `reopened_at_gmt` on the latest entry): one entry per completed-and-reopened cycle, decided on a locked read, so two stale callback transitions cannot write two entries and no request-scoped memo is needed. A wp-admin status flip into a paid status on a reopened sale that still has captured rows is stamped (and recorded fiscally) as a re-completion by the register that last took money; it is a close by other means.
8. **`close` completes a zero-total open order** (§4.3; ruled by Paul on 2026-10-20, reversing the earlier "refused" reading): WooCommerce completes a zero-total checkout through `payment_complete()` without a gateway (`needs_payment()` false, `process_order_without_payment()`), and after PR 1 the till had no path left for a fully discounted sale (the ledger never completes a zero total, the push refuses a paid status). The till's zero-balance completion becomes a `close` (client handoff item 3). Shipped in the PR after #2365.
9. **The sale record's signed adjustment lives in the payload** (§4.7): the closure `adjustments` counters are ruled in the wiki and not built on `next`; building them is a closure-fold item, not PR 2's.
10. **Pro's `Refund_Processor` reads an authorization-only order as a pre-ledger sale** after D6 (§4.1) and would fall through to its gateway refund dispatch, which the provider refuses on an uncaptured authorization. Nothing is charged; the tidy-up (an `authorized` row means "nothing to refund") is a Pro PR, not this one.
11. **`wcpos_sale_completed` is the fiscal sale trigger** (§4.7), replacing `woocommerce_payment_complete` in `Fiscal_Record_Writers`. A completion the stamp does not write (a storefront payment) therefore writes no sale, which is the ADR's "completed through a register" condition made mechanical; a fiscal row whose completion was reopened before the row landed is left to the human the failure note already named.
12. **`record`'s mismatched replay becomes 422 `wcpos_command_conflict`** (§5.2), replacing its 409 `wcpos_payment_conflict`: a same-id-different-body answer is one code across the family. `wcpos_payment_conflict` stays for the state conflicts (`submit` on a cancelled or superseded attempt, a live payment already on the order). No shipped client speaks the 409 (D1).
13. **A refusal that changed nothing stores no command outcome** (§5.2): a provider decline, a lock timeout, a balance refusal or a validation error leaves no entry, so the same command id retried runs again. The alternative (storing every answer, Stripe-style) would replay a transient provider outage forever and needs an expiry the ADR's consequences paragraph argues against. The one stored refusal is `record`'s failed row, which exists today.
14. **Every 2xx money answer carries `revision`** (§5.3), the canonical revision after the command, so the till chains `record` → `close` without a pull. It costs one bare wc/v3 read per command on top of the one the compare already needs; the status poll, which is called every few seconds during a card payment, carries neither field and returns no revision.
15. **`revision` is required on `record` too** (§5.1): an offline cash row arriving against a stale revision is refused and re-sent by the till with the same row id (one row), rather than accepted blind. The ADR's "offline cash rows replay days later and create one row" is the replay-by-row-id case (5.6 #16), which the revision never blocks.
16. **A stranded refund allocation answers the stored row, never an error** (§6.1, §6.2): when the settle does not land, the handler throws, or its error is indeterminate, `Ledger::refund()` returns the row with the `pending` allocation, the route answers 200 `{payment, revision}` with the allocation `pending` (the next order summary the till reads shows `refund_pending`), and the order carries the note. The alternative, an error, is thrown by Pro's `woocommerce_create_refund` hook and makes WooCommerce delete the refund after the provider may have refunded: rule 8's exact failure. The till's true state is "sent, unconfirmed", and that is what it is told.
17. **No human-facing settle surface in PR 4** (§6.2): a stranded `pending` allocation blocks reopen (rule 3), shows as `refund_pending`, and is settled by a developer with `Ledger::settle_allocation()` after a human confirms at the provider. Reaching it takes a storage failure inside one locked request after the provider answered, or a gateway that throws mid-refund; a wp-admin action is a follow-up only if it happens in the wild.
18. **Rule 7's sweeper clause holds for provider legs, not for WooCommerce gateway attempts** (§6.3): the WooCommerce gateway API has no lookup by reference, so a `sent` attempt is resolved by the gateway's completion, the till's `cancel`, or a newer send, and blocks reopen until one of those happens. PR 4 verifies the provider-leg half (pins exist; one added if missing) and changes nothing on the attempt half.
19. **Client-handoff item: the till sends `api_refund: true` for original-method refunds** (§6.4, monorepo `use-refund-mutation.ts`, both lanes), where the handoff expected `false`. Under ADR 0040 the provider refund belongs to the allocation; the client handoff PR 5's agent writes must carry it.
