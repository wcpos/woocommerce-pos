# How WooCommerce plugins model one purchase paid by several payments

Research for [wcpos/roadmap#116](https://github.com/wcpos/roadmap/issues/116); feeds the split-payment
decision (#107) and the ledger decision (#103). **Facts and observed consequences only — no
recommendation.** Anything not backed by primary material is marked **unverified**.

Core citations are `path:line` against the local WooCommerce **10.4.3** tree
(`/Users/kilbot/.wp-env/wp-env-woocommerce-pos-cf9da277/woocommerce/`). Plugin citations are against
source pulled from wordpress.org on 2026-08-28 (versions named per section) and the public
`Automattic/woocommerce-subscriptions-core` repository. WooCommerce Deposits has no public source;
its section says exactly which evidence is primary and which is secondary.

## 2. Per-plugin notes

### WooCommerce Subscriptions — the canonical Woo parent/child pattern

Source: `Automattic/woocommerce-subscriptions-core` (public GitHub, HEAD 2026-08-28), cited `SUBS/…`.

- **The parent link runs the opposite way to intuition, and renewals are not children.** `shop_subscription` is registered via `wc_register_order_type()` with every exclusion flag set — `exclude_from_order_count/_views/_webhooks/_reports/_sales_reports => true`, `class_name => WC_Subscription` (`SUBS/includes/class-wc-subscriptions-core-plugin.php:386-434`). The *subscription* is the child of the initial checkout order: `$subscription->set_parent_id( $args['order_id'] )` (`SUBS/wcs-functions.php:185-186`, called at `SUBS/includes/class-wc-subscriptions-checkout.php:134-143`). **Renewal orders are created with `parent_id = 0`** — `wcs_create_order_from_subscription()` passes `wc_create_order()` only `customer_id`, `customer_note`, `created_via => 'subscription'`, no `parent` (`SUBS/includes/wcs-order-functions.php:228-234`). The renewal↔subscription link is **order meta** `_subscription_renewal` (`SUBS/includes/data-stores/class-wcs-related-order-store-cpt.php:27-31,85-107`; `SUBS/includes/wcs-renewal-functions.php:35`), and Subs queries renewals by meta, never by `wc_get_orders(['parent'=>…])` (`class-wcs-related-order-store-cpt.php:41-58`).
- **Every renewal is a complete, self-contained order.** Items/fees/shipping/tax/coupons are re-added from the *subscription* (not the initial order) via `wcs_copy_order_meta()` + `wc_add_order_item()` + `wcs_copy_order_item()` (`SUBS/includes/wcs-order-functions.php:236-262`). `_order_stock_reduced` is in `DEFAULT_EXCLUDED_META_KEYS` (`SUBS/includes/class-wc-subscriptions-data-copier.php:19-45`), so **each renewal reduces stock in its own right**.
- **`payment_method` is stamped per renewal**, explicitly, after creation: `$renewal_order->set_payment_method( wc_get_payment_gateway_by_order( $subscription ) )` (`SUBS/includes/class-wc-subscriptions-manager.php:163-166`; helper `wcs_copy_payment_method_to_order()` at `SUBS/includes/wcs-order-functions.php:911-925`). `_payment_method`/`_payment_method_title` are deliberately excluded from the generic meta copy (`class-wc-subscriptions-data-copier.php:35-36`); manual renewals are left with no gateway (`class-wc-subscriptions-manager.php:159-162`).
- **Statuses:** renewals use ordinary `shop_order` statuses (`pending` → `processing`/`completed`/`failed`). Custom statuses live only on the subscription object (`wc-active`, `wc-on-hold`, `wc-pending-cancel`, `wc-switched`, `wc-expired` — `SUBS/wcs-functions.php:216-229`).
- **Analytics:** because renewals carry `parent_id = 0`, every `parent_id = 0` guard passes — each renewal is +1 `orders_count` with its own `gross_sales`/`net_revenue`/`total_sales`. **N payments show as N independent orders: no double counting, no netting.** The subscription object is never synced (Analytics only accepts `shop_order`/`shop_order_refund`, §3); note `exclude_from_order_reports` is a *legacy*-reports flag that Analytics never reads.
- **Admin/customer UI is entirely plugin-supplied.** Renewals are ordinary un-indented Orders rows; Subs adds a "contains subscription" column (`SUBS/includes/class-wc-subscriptions-order.php:27-36`), a **Related Orders metabox** on both the subscription and the order edit screen (`SUBS/includes/admin/class-wcs-admin-meta-boxes.php:89,103`; renderer `SUBS/includes/admin/meta-boxes/class-wcs-meta-box-related-orders.php`), and `SUBS/templates/myaccount/related-orders.php`.
- **Refunds** attach to the renewal that took the money and resolve the gateway from that order's own `payment_method`. `WC_Subscription::get_refunds()`/`get_total_refunded()` (`SUBS/includes/class-wc-subscription.php:2018-2038`) exist only to satisfy the edit-order UI.
- **Numbering/emails:** no custom numbering (`grep woocommerce_order_number SUBS/includes/` is empty) — a renewal gets an ordinary sequential id. Subs swaps core order emails for renewal variants (`new_renewal_order`, `customer_processing_renewal_order`, `customer_completed_renewal_order`, `customer_on_hold_renewal_order`, `customer_renewal_invoice`) on the same transitions, gated on `wcs_order_contains_renewal()` (`SUBS/includes/class-wc-subscriptions-email.php:69-115,157-172`).
- **Known problems:** [subscriptions-core#838](https://github.com/Automattic/woocommerce-subscriptions-core/issues/838) (status widget + legacy Subscriptions report vanish under HPOS with compatibility mode off); [woocommerce#65961](https://github.com/woocommerce/woocommerce/issues/65961) (duplicate renewal orders — both `parent_id = 0`, so both count); [subscriptions-core#702](https://github.com/Automattic/woocommerce-subscriptions-core/issues/702) (a lost `_subscription_renewal` meta orphans the child, because meta is the only join). No report found of renewals double-counting or vanishing from Analytics — **unverified** that one exists.

### WooCommerce Deposits (official Woo extension)

Source is not public. Primary: [woocommerce.com/document/woocommerce-deposits/](https://woocommerce.com/document/woocommerce-deposits/). **Secondary evidence** (labelled as such throughout): the GPL fork [`Veraxus/wc-deposits-with-variations`](https://github.com/Veraxus/wc-deposits-with-variations), a v1.x-era copy of the real plugin — older than the current release, so treat line numbers as indicative.

- **Parent + children linked by `post_parent`** — `wc_create_order([... 'created_via' => 'wc_deposits'])` then `wp_update_post(['post_parent' => $original_order_id])` (fork, `includes/class-wc-deposits-order-manager.php:171-232`). An item-level back-pointer `_original_order_id` is written as order *item* meta, not order meta (`:220`), alongside `_remaining_balance_order_id`, `_remaining_balance_paid`, `_payment_plan`, `_is_deposit`, `_deposit_full_amount` (`:262-268`).
- **Not a zero-total parent.** The parent carries real product line items whose **price has been rewritten to the deposit amount** (`$cart_item['data']->set_price( $cart_item['deposit_amount'] )`, fork `cart-manager.php:237`); the full price survives only as item meta `_deposit_full_amount` (`:343-344`). Each follow-up order gets a **real product line item** priced at that instalment, then `calculate_totals()` (`order-manager.php:209-222`). Stock is gated through `woocommerce_can_reduce_order_stock` / `woocommerce_payment_complete_reduce_order_stock` (`:49-50`).
- **`payment_method` is not copied to the child** — `create_order()` copies customer id, note and both addresses only (`order-manager.php:174-200`); the child is left unpaid for the customer to pay at its own pay-URL.
- **Two custom statuses:** `wc-partial-payment` ("Partially Paid") and `wc-scheduled-payment` ("Scheduled") (`order-manager.php:72-99`), both added to `woocommerce_valid_order_statuses_for_payment_complete` (`:107-110`), with the parent forced to `partial-payment` via `woocommerce_payment_complete_order_status` (`:115-120`). **Neither is added to `woocommerce_order_is_paid_statuses`.**
- **No Analytics code at all — and the consequence is a documented core bug.** [woocommerce-admin#4050 "Unexpected Order Statuses Included in Analytics"](https://github.com/woocommerce/woocommerce-admin/issues/4050) names `wc-partial-payment` and `wc-scheduled-payment` from this plugin by name and reports Analytics totals disagreeing with the legacy reports (closed via PR #4090; repo archived 2024-07-12). Both statuses count by default (§3), and the children carry `parent_id != 0`, so their money lands in Net sales/Total sales but not Gross sales or Orders count.
- **Refunds are manual**, per the official docs: refunds "will need to be refunded manually from the order". No `wc_create_refund` in the fork.
- **Customer-facing:** children are real orders with their own numbers, shown as "**Remainder – Invoice #%s**" (`order-manager.php:309,437`); `wc-scheduled-payment` orders are **hidden from My Account** via `woocommerce_my_account_my_orders_query` (`:126-128`). Follow-up payment uses the standard customer-invoice email. Also reported: [mollie/WooCommerce#138](https://github.com/mollie/WooCommerce/issues/138) — order status latches on "Partially Paid".

### YITH Deposits and Down Payments (free, 1.2.2) — split the line-item price across two real orders

- **Parent + suborder via `post_parent`** (`includes/class.yith-wcdp-suborders.php:420-436`), suborder identified by `_created_via = 'yith_wcdp_balance_order'` plus a non-zero parent (`:600-603`); cross-links `_has_deposit`, `_full_payment_orders`, item meta `_full_payment_id` / `_deposit_id` (`:448-458`).
- **Both orders carry real product line items and neither is zero-total.** Parent item price = the deposit (`includes/class.yith-wcdp.php:253`); the suborder is built by re-adding the same product to a scratch cart with the price forced to the balance, then `WC()->checkout()->create_order()` + `calculate_totals()` (`class.yith-wcdp-suborders.php:159-168,405,441`). **No fee line is used.** The suborder is stamped `_order_stock_reduced => true` and `_recorded_sales => 'yes'` at creation to suppress a second stock decrement and a second legacy sales count (`:425-436`).
- **`payment_method` is inherited accidentally**: the suborder goes through `WC_Checkout::create_order( $posted_data )`, which does `$order->set_payment_method( $data['payment_method'] )` (`includes/class-wc-checkout.php:456`), then is forced to `pending` (`:422`). Both orders therefore name the same gateway even though only one was charged.
- **No custom statuses** — no `register_post_status` anywhere; the suborder is plain `pending` (filter `yith_wcdp_suborder_status`) and syncs to `cancelled`/`failed` with the parent (`:69-70,291-305`).
- **No Analytics code.** Consequence: the deposit order counts normally; the balance suborder is excluded while `pending`, but **the moment it is paid and flips to processing/completed it counts in Total sales / Net sales while `parent_id != 0` keeps it out of Gross sales and Orders count** — the two figures then differ by exactly the balance. The only double-count the plugin defends against is the legacy per-product counter (readme changelog: *"avoid WooCommerce increasing sales counter twice for a product purchased with deposit"*).
- **No refund handling** (no `wc_create_refund`, no `woocommerce_order_refunded`). The suborder is a normal `shop_order` with its own number, visible in My Account, payable at its own URL, with standard emails; a "My Deposits" table lists paid vs outstanding (`templates/my-deposits.php`).
- **Support threads:** nothing on reporting; nearest are ["Full Payment Order is Missing"](https://wordpress.org/support/topic/full-payment-order-is-missing/) and ["COUPON DOESNT APPLY ON THE TOTAL PRICE, IT APPLIES ONLY ON DEPOSIT"](https://wordpress.org/support/topic/coupon-doesnt-apply-on-the-total-price-it-applies-only-on-deposit/).

### Acowebs, Bayna/codeixer and MagePeople — full parent + fee-only children on a custom order *type*

Three plugins converge on the same shape. **All three keep the complete line items, taxes, shipping and the FULL total on the parent `shop_order`, and make each instalment a child of a custom order type carrying a single `WC_Order_Item_Fee`.** This is the exact inverse of the zero-total-parent premise.

- **Acowebs, Deposits & Partial Payments 1.2.12** — type `awcdp_payment` (`wc_register_order_type`, `includes/class-awcdp-deposits.php:44-91`), `set_parent_id()` at `includes/class-awcdp-front-end.php:1818,1929`; child = one fee item `"Partial Payment for order %s"` with `set_total($amount)` (`:1806-1830`). Stock reduces on the *parent* when it reaches `partially-paid` (`:118`). `payment_method` is set on the **deposit (first) child only** (`:1859`, blocks path `:1975`); later instalments get none; a `bacs` child back-stamps `bacs` onto the parent (`:2173-2174`). Status `wc-partially-paid` (`class-awcdp-deposits.php:96-106`), added to `woocommerce_valid_order_statuses_for_payment_complete` and `woocommerce_order_has_status` but **not** to paid statuses. `AWCDP_Order::get_order_number()` returns the **parent's** number on the thank-you page and its own id everywhere else (`includes/class-awcdp-order.php:228-233`); new-order/on-hold/completed emails suppressed for payment orders, with a dedicated `awcdp_deposit_paid` email.
- **Bayna / codeixer, Deposits & Partial Payments 1.4.3** — type `shop_deposit` (`src/Bootstrap.php:324-366`); exactly **two** children, `"Deposit Payment for order #{id}-1"` and `"Due Payment for order #{id}-2"` (`src/Checkout.php:475-513`), each with `$item->set_total_tax(0)` and `calculate_totals( apply_filters('bayna_apply_tax_calculate_totals', false) )` — **children carry no tax by default**. Deposit child inherits the parent's method (`:507`); the Due child gets none. Status `wc-deposit` (`src/Bootstrap.php:374-396`); parent flips to an admin-chosen `bayna_fully_paid_status` once all children are completed (`:369-381`). Zero refund handling (`grep refund src/` is empty).
- **MagePeople / WpDepositly, `advanced-partial-payment-or-deposit-for-woocommerce` 3.1.0** — type `mepp_payment` (`inc/mepp-functions.php:246-289`). Two child modes via option `mepp_partial_payments_structure` (`:792`): `single` (one fee line, `:804-817`) or **itemized**, which copies real line items onto the child and flags `_mepp_partial_payment_itemized` (`:822-828`) — the only per-instalment itemized child in the survey. Status `wc-partially-paid`. **The only deposits plugin here that ships its own report — and it is a legacy one**: `add_filter('woocommerce_admin_reports', …)` registering an `orders → deposits` report built on `WC_Admin_Report` (`advanced-partial-payment-or-deposit-for-woocommerce.php:401-416`, `inc/admin/class-mepp-admin-reports.php:10-239`). No WC Analytics integration.
- **Shared Analytics consequence for all three:** the custom type is **never synced into `wc_order_stats`** (§3), so the instalment children are invisible to Analytics — but the parent's **full** order value is recognised the instant the deposit is paid, because none of `partially-paid` / `deposit` is in the default exclusion list. **Analytics can therefore never tell the merchant what has actually been collected.** The `exclude_from_order_reports` / `exclude_from_order_sales_reports` flags these plugins set (Acowebs `class-awcdp-deposits.php:80-81`; Bayna deliberately leaves `exclude_from_order_sales_reports => false`, `src/Bootstrap.php:362`; MagePeople has both **commented out**, `inc/mepp-functions.php:282-283`) affect *legacy* reports only, so Bayna and MagePeople double-count in the legacy reports while Acowebs does not.
- **Support-thread confirmation** on the legacy side: on ["Deposit not showing on Reports"](https://wordpress.org/support/topic/deposit-not-showing-on-reports/) the Acowebs contributor's fix is `add_filter('woocommerce_reports_order_statuses', …)` to add `partially-paid` — the custom status is out of legacy reports by default. Also [Critical compatibility issue: `woocommerce_order_is_paid` filter returns an array](https://wordpress.org/support/topic/critical-compatibility-issue-woocommerce_order_is_paid-filter-returns-an-array/) (Acowebs Pro 3.1.8 breaks `$order->is_paid()`, causing duplicate Subscriptions renewals), [Deposit payment not updating stock quantity](https://wordpress.org/support/topic/deposit-payment-not-updating-stock-quantity/), and for Bayna [Collecting deposits and then do partial refund](https://wordpress.org/support/topic/collecting-deposits-and-then-do-partial-refund/) — the author's answer sidesteps refunds entirely.

### SR Partial Payments 1.3.8 — the one-order model

- **One order. No children, no parent link, no custom order type.** Payments go to a custom table `{prefix}srpp_partial_payments` (`includes/class-ppp-activator.php:37-50`, first row at `includes/class-ppp-order-handler.php:44-63`).
- **The order keeps its full, correct total in the DB, deliberately.** The code comment is explicit: *"we no longer override the total permanently in the DB via `set_total()`. Doing so overwrites the grand total permanently and breaks invoices and reporting. Instead, we dynamically filter `woocommerce_order_get_total` exactly when the gateway executes…"* — `includes/class-ppp-gateway.php:66-70`. The split lives in meta (`_ppp_is_partial`, `_ppp_paid_amount`, `_ppp_cod_amount`, `_ppp_original_total`) and the surcharge is a normal non-taxable cart fee (`includes/class-ppp-checkout.php:221`).
- One `payment_method` (the online gateway); the balance is collected as COD, off-ledger. Status `wc-partial-payment` (`class-ppp-order-handler.php:69-99`), not added to paid statuses. **Analytics revenue is correct in amount but recognises the full value at checkout** — it cannot distinguish collected from owed. No refund handling (the table has a `refunded` enum value that nothing writes). wp.org forum has **zero topics**.

### Order Splitter for WooCommerce 5.3.8 — the only plugin that repairs `wc_order_stats` by hand

Different problem (splitting fulfilment, not tender), but it is the clearest primary-source acknowledgement that two orders holding parts of one purchase double-count.

- **Children are full top-level `shop_order`s with `post_parent = 0`**; the link is order meta `splitted_from` / `cloned_from` plus `_wc_os_child_order = 'yes'` (`inc/functions.php:2817,3180,…`; lookup `inc/functions-inner.php:350`). Line items are **moved, not duplicated** (`splitted_order_items`, `inc/functions.php:4321`) — the original can end up with no items at all. `payment_method` / `payment_method_title` are copied verbatim (`inc/functions.php:3795-3796`). No custom statuses.
- **It de-duplicates `wc_order_stats` manually.** Hooks `woocommerce_analytics_update_order_stats` and the product/coupon/tax variants (`inc/functions-inner.php:929-932`), then: `DELETE FROM {prefix}wc_order_stats WHERE order_id = {child}` while the parent still has items — *the child's revenue is erased so the intact parent isn't double-counted* (`:1039-1046`) — or `DELETE … WHERE order_id = {parent}` once the parent is emptied, flipping `_wc_os_report_included` (`:958-970,1015-1030`); same for the product/coupon/tax lookup tables, then `ReportsCache::invalidate()`.
- No refund handling. Known problem: children re-fire the new-order email because `_new_order_email_sent` is deleted on clone (`inc/functions-inner.php:634`) — reported at [Splitted orders send duplicates emails](https://wordpress.org/support/topic/splitted-orders-send-duplicates-emails/) and [Woocommerce send email before the split](https://wordpress.org/support/topic/woocommerce-send-email-before-the-split/).

### POS plugins claiming split tender

Source: current wp.org releases, extracted 2026-08-28. **Not one of them uses child orders.**

- **Oliver POS 4.9.3** — synthetic gateway `oliver_pos_split` / `payment_method_title = "Split Payment"` (`includes/orders/class-order-handler.php:47,469-479`; `includes/orders/class-order-queue.php:927-936`). Breakdown → order meta **`_oliver_pos_payments`**, written verbatim from the device payload with **no schema, sanitization or shape validation** (`class-order-queue.php:949-951`); it is not in the `register_order_meta()` allowlist (`class-order-handler.php:70-97`), so it is neither REST-exposed nor rendered in the admin order screen. Five label-only gateways are registered (`oliver_pos_cash|card|card_integrated|split|other`, `:128-140`). **No `wc_create_refund`/`wc_refund_payment` call anywhere** — the app refunds over WC REST, where core resolves the gateway from `oliver_pos_split`, which supports no refunds. Its own payment report does `GROUP BY o.payment_method` (`includes/reports/class-report-payments.php:96-146`), so a split reports 100% under "Split Payment" and `_oliver_pos_payments` is never queried. Register session: `oliver_shift` CPT + custom table `wp_oliver_cash_ledger` (`includes/cash/class-cash-ledger.php:33-70`), with shift totals bucketed only cash-vs-card (`includes/class-money-backfill.php:48-55`).
- **FooSales 1.42.8** — split tender since 1.38.0: *"Starting with version 1.38.0, FooSales now supports split payments. The method for recording payments on orders has been updated to include this feature."* (`admin/helpers/foosales-phrases-helper.php:154`). Single gateway `foosales-split` / "Split Payment" (`admin/helpers/foosales-api-helper.php:2039-2041`), **plus three parallel records**: order meta `_foosales_payment_method`; order meta **`_foosales_payments`**, a JSON array with one object per tender (`pd` date, `opmk` method key, `oud` cashier, `tid` txn id, `pa` amount, `pn`/`np` payment number, `pap` paid, `par` refunded — `:2471-2500`); and a **`foosales_payment` custom post type, one post per tender** (`admin/class-foosales-payments.php:52-127,698-770`). An admin metabox lists the tenders and self-heals `_foosales_payments` from the payment posts (`admin/class-foosales-admin.php:3206-3245`), and a dedicated "POS Payments" list table is the payment report — built off the payment posts, not WooCommerce reports. **The only per-tender refund in the survey**: `wc_create_refund()` once for the total (`foosales-api-helper.php:3664`), then a per-tender loop marking each `par=1` and reversing **Square/Stripe legs only** by transaction id (`:3559-3600,3701-3748`). Their docs are explicit that *"refunding an order through the WooCommerce interface in your WordPress admin dashboard will not automatically refund split payments"* (help.fooevents.com/docs/topics/point-of-sale/payments/split-payments/).
- **Jovvie 5.20.6 (BizSwoop)** — supports split tender **in code while the public docs deny it**: gateway `pos_split_payment` / "Split Payment" (`includes/Gateway/SplitPayment.php:12-14`), enabled by default (`includes/Admin/Tabs/Gateway.php:156-159`), whereas jovvie.com/documentation/payment-gateways-docs/ says *"the POS doesn't support split payments functionality… If or when WooCommerce adds split payments functionality, we will definitely add the support."* — treat that page as stale. Breakdown → `_pos_split_payments`, `_pos_successful_split_payments` and per-gateway keys `pos-<gateway>-tendered` (`SplitPayment.php:44-47,61,130-155`). `process_payment()` sums the legs, checks integer-cents equality against the total, then fans out to each child gateway's own `process_payment()`, tracking successes so a retry only re-runs failed legs (`:52-127`) — the cleanest split mechanism in the set. Refunds go through `wc_create_refund()` against the single `payment_method`, with `gateway_supports_refunds()` checked against that one id and **no cashier tender picker** (`includes/API/Refunds.php:397-399,527-560`). Its own `ReportSalesByGateway` filters `where_meta _payment_method = $gateway` (`includes/Admin/Reports/ReportSalesByGateway.php:58-68`), so splits collapse to one bucket. Register session: `wp_pos_till_sessions` + `wp_pos_till_events` (`includes/CashManagement/Database.php:16-77`) — and this is **the only place in any surveyed plugin where the split is decomposed into a ledger**: `$is_split_with_cash = $payment_method === 'pos_split_payment' && pos-cash-tendered > 0`, with `meta['is_split_payment']` on the event (`includes/CashManagement/OrderHooks.php:37-42,113-121,159-164`).
- **WebPOS 1.2.0 (VillaTheme)** — multi-method in the UI, **but the breakdown never reaches the server**. `payment_method` is the literal string `'multi'` (no such gateway is registered) and `payment_method_title = "Multiple Methods"` (`includes/frontend/orders.php:56,100-105`); only `pos_total_paid` and `pos_change` are stored. The client builds `payments.paid = {cash: x, card: y, …}` (`assets/js/frontend-pos-data.js:1292-1316`) but PHP reads only `is_paid`/`total_paid`/`change` — **`payments['paid']` is never iterated in PHP**. Its custom table `wp_viwebpos_transactions` gets exactly one row per order with `method = 'multi'` (`includes/class/class-transaction-table.php:17-34`, `orders.php:150-163`), so the receipt's "per-method" rendering shows a single row labelled `multi`. The per-tender amounts are lost at write time. No refund code at all.
- **wePOS 2.0.1 (weDevs)** — **does not support split tender.** One gateway, `wepos_cash` (`includes/Gateways/Cash.php:39`); the only tender meta are `_wepos_cash_tendered_amount` / `_wepos_cash_change_amount` (`:115-118`); grep for `split|multiple payment|partial payment` across `build/*.js`, `assets/js/*.js` and `languages/*.pot` returns nothing; one order = one gateway, matched by exact id at `includes/REST/PaymentController.php:108`. No custom tables, no register session, no payment report in the free plugin (Pro documents a "Payment Reports" page — **unverified**).
- **Point of Sale for WooCommerce (Actuality Extensions)** — **no primary source obtainable.** The woocommerce.com product page now serves a retired-product notice (fetched 2026-08-28) and `support.actualityextensions.com` does not resolve (DNS ENOTFOUND). Third-party round-ups claim split support; **unverified** — nothing is known about its meta keys, gateway ids, refunds or register model.

**Common pattern across the POS plugins.** (1) Every one that supports a split parks the order on **one synthetic gateway** — `oliver_pos_split`, `foosales-split`, `pos_split_payment`, or WebPOS's bare non-gateway string `'multi'` — with `payment_method_title` "Split Payment"/"Multiple Methods", never a composed "Card + Cash". (2) The breakdown always lands in **order meta the POS invented and only the POS reads**; only FooSales gives tenders first-class records. (3) All of them bypass WooCommerce reporting for payment-method analysis — yet Oliver and Jovvie still group their *own* reports by the single `_payment_method` column, so the split collapses back to one bucket even there. (4) Refunds are the weakest seam everywhere, because `wc_refund_payment()` resolves the gateway from the split pseudo-gateway. (5) **The cash-drawer/register ledger, not the order, is where the split survives** (Oliver's `wp_oliver_cash_ledger`, Jovvie's till tables, WebPOS's transactions table) — so an accounting connector reading only WooCommerce sees "Split Payment" and nothing else.

## 3. WooCommerce core facts the models depend on

`path:line` = WooCommerce **10.4.3** at `/Users/kilbot/.wp-env/wp-env-woocommerce-pos-cf9da277/woocommerce/`.

**`parent_id` on orders.** CPT: the post's `post_parent`; `WC_Data_Store_WP` maps query var `parent` → `post_parent`, `parent_exclude` → `post_parent__not_in` (`includes/data-stores/class-wc-data-store-wp.php:312-313`). HPOS: a real column `parent_order_id bigint(20) unsigned null` with `KEY parent_order_id` (`src/Internal/DataStores/Orders/OrdersTableDataStore.php:3227,3240`), and `OrdersTableQuery` maps `parent` → `parent_order_id` plus the CPT spellings `post_parent`, `post_parent__in`, `post_parent__not_in` (`src/Internal/DataStores/Orders/OrdersTableQuery.php:279-281,310,736`). So **`wc_get_orders(['parent'=>123])` behaves identically on both backends**, and nothing in core forbids a `shop_order` being the child of another `shop_order` — core just never does it itself: every internal parent join is hard-filtered to `shop_order_refund` (`includes/data-stores/class-wc-order-data-store-cpt.php:446,469,493`; `OrdersTableDataStore.php:1058,1088,1116`).

**Analytics: `wp_wc_order_stats` has a `parent_id` column** — `includes/class-wc-install.php:1254-1277` (`parent_id bigint(20) unsigned DEFAULT 0 NOT NULL`, `KEY idx_date_paid_status_parent`). It is written from `$order->get_parent_id()` for **every** order, not only refunds (`src/Admin/API/Reports/Orders/Stats/DataStore.php:545`); the refund-only fixups are in the `'shop_order_refund' === $order->get_type()` branch at `:577-596`. Only `shop_order` and `shop_order_refund` are synced at all (`:499-501`, `:625`; `src/Internal/Admin/Schedulers/OrdersScheduler.php:317`) — **a custom order type is invisible to Analytics unconditionally**, whatever its `wc_register_order_type()` flags say (those flags feed legacy reports only).

**How `parent_id` changes the arithmetic** (`src/Admin/API/Reports/Orders/Stats/DataStore.php:107-131`):

| Metric | SQL | rows with `parent_id != 0` |
|---|---|---|
| `orders_count` | `SUM( CASE WHEN parent_id = 0 THEN 1 ELSE 0 END )` | **excluded** |
| `gross_sales` | `SUM( CASE WHEN parent_id = 0 THEN total_sales-tax-shipping ELSE 0 END ) + coupons` | **excluded** |
| `avg_order_value`, `avg_items_per_order` | same `parent_id = 0` guard | **excluded** |
| `total_sales`, `net_revenue` ("Net sales"), `taxes`, `shipping`, `num_items_sold` | plain `SUM(...)` | **included** |
| `refunds` | `ABS( SUM( CASE WHEN net_total < 0 … ) )` | by sign, not by parent |

So a **child order with a positive total lands in Total sales / Net sales / Taxes / Shipping / Items sold, but not in Orders count or Gross sales.** Two further places equate `parent_id != 0` with "is a refund":
- `src/Admin/API/Reports/Orders/Stats/Segmenter.php:75` — `'refunds' => "SUM( CASE WHEN parent_id != 0 THEN total_sales END ) AS refunds"`. In any segmented view (by product/coupon/category) a positive-total child is reported as a **positive refunds figure**.
- `src/Admin/API/Reports/DataStore.php:1083-1100` — the Orders report's `refunds` filter: `all` → `parent_id != 0`, `none` → `parent_id = 0`, `full`/`partial` → join `parent_order_stats` on `parent_id`. A child `shop_order` is classified as a refund row.

`parent_id` is a returned column of the Analytics Orders report (`src/Admin/API/Reports/Orders/DataStore.php:75,105`, related-order resolution at `:371,452-456`), but there is **no Analytics setting or advanced filter for child/parent orders**. The one seam for changing what an order writes into `wc_order_stats` (its `parent_id` and totals included) is `apply_filters( 'woocommerce_analytics_update_order_stats_data', $data, $order )` — `Orders/Stats/DataStore.php:573`.

**Status exclusion.** `get_excluded_report_order_statuses()` reads option `woocommerce_excluded_report_order_statuses`, default `['pending','failed','cancelled']`, merges `auto-draft`/`trash`, filter `woocommerce_analytics_excluded_order_statuses` — `src/Admin/API/Reports/DataStore.php:799-802`, applied at `:1357-1361`; setting UI `src/Internal/Admin/Settings.php:314-315`. Woo docs: *"Custom order statuses are included by default but can be manually excluded"*, *"The Refunded status cannot be excluded"* (<https://woocommerce.com/document/woocommerce-analytics/>). **A plugin's `partial-payment`-style status counts in Analytics unless the merchant opts it out.**

**No payment-method dimension exists in WooCommerce reporting.** `grep -rn payment_method src/Admin/API/Reports/` → **0 hits** in 10.4.3, and the legacy set (`includes/admin/reports/`) is sales-by-date/-product/-category/-coupon, taxes, customers, stock — there is no sales-by-payment-method report anywhere in core.

**Order-type registry (legacy reports only).** `wc_register_order_type()` accepts `exclude_from_order_count`, `exclude_from_order_reports`, `exclude_from_order_sales_reports`, `exclude_from_order_views`, `exclude_from_order_webhooks` (`includes/wc-order-functions.php:342-374`, consumed by `wc_get_order_types()` at `:228-`); legacy reports select by type, not parent (`includes/admin/reports/class-wc-report-sales-by-date.php:71,107,139,167,209`).

**Orders admin list.** Neither list table filters on the parent link (no `post_parent` in `includes/admin/list-tables/class-wc-admin-list-table-orders.php`; `parent` in `src/Internal/Admin/Orders/ListTable.php` matches only `parent::` calls). **Child `shop_order`s appear as ordinary top-level rows with their own numbers**, on both backends. Core has no "related orders" UI for a `shop_order` parent and no `WC_Order::get_related_orders()`.

**REST `wc/v3/orders`.** `parent_id` is a schema field and is **not** `readonly` (`includes/rest-api/Controllers/Version2/class-wc-rest-orders-v2-controller.php:1159-1163`), so a child can be created in one POST; `_links.up` is emitted when it is non-zero (`:609-612`). `WC_REST_Orders_V2_Controller extends WC_REST_CRUD_Controller` and sets `$hierarchical = true` (`:27,56`), which turns on the `parent[]` / `parent_exclude[]` collection params defined at `includes/rest-api/Controllers/Version3/class-wc-rest-crud-controller.php:672-690` and applied as `post_parent__in`/`post_parent__not_in` at `:297-298`; under HPOS the controller routes through `WC_Order_Query` (`class-wc-rest-orders-v2-controller.php:2131-2151`) which maps those keys to `parent_order_id`. **`GET wc/v3/orders?parent[]=123` works on both backends, and `parent_exclude[]` is the only way to keep children out of a default listing.**

**Refunds and gateways.** `wc_refund_payment( $order, $amount, $reason )` resolves the gateway from **that order's own scalar `payment_method`** and throws *"The payment gateway for this order does not exist."* otherwise — `includes/wc-order-functions.php:764-798` (`:772`, `:776`, REFUNDS-support check `:779-781`); the same lookup lives in `wc_get_payment_gateway_by_order()` (`:882-895`). **Whichever order carries a tender's `payment_method` is the only order that can drive that tender's automated refund.**

**Paid statuses and stock.** `wc_get_is_paid_statuses()` = `processing` + `completed`, filter `woocommerce_order_is_paid_statuses` (`includes/wc-order-functions.php:134-143`). Stock reduction hooks `woocommerce_payment_complete` / `…_status_completed` / `…_status_processing` / `…_status_on-hold`, idempotent per order via `_order_stock_reduced` (`includes/wc-stock-functions.php:104-127`): **an order parked in a custom status never fires a reduce hook**, and an order with no line items reduces nothing. Order numbers are `$order->get_id()` through the `woocommerce_order_number` filter (`includes/class-wc-order.php:579`).

**Accounting connectors key on the single `payment_method`.** Official Woo Xero extension: *"The extension uses the single Payment Account configured above for every WooCommerce payment gateway."* (<https://woocommerce.com/document/xero/>) — one store-wide account, no per-gateway routing. MyWorks Sync (Xero/QuickBooks): *"Mapping your WooCommerce payment methods ensures that as orders sync from WooCommerce to Xero, the payments are sent to the desired bank account in Xero"*, with one mapping section *"for each payment method that's currently active on your WooCommerce store"* (<https://support.myworks.software/en/articles/13538272-setting-up-myworks-connecting-woocommerce-to-xero>); neither doc addresses an order with more than one payment method. **Net effect: a sale reaches the ledger through exactly one `payment_method` per Woo order.**

## 4. Ideas worth taking / traps

### On the owner's working premise — "a parent order with 0 total, and sub-orders with the partial totals"

**No surveyed plugin does that.** Three families exist and none zeroes the parent: *split the line-item price across parent and child* (WooCommerce Deposits, YITH — both orders hold real, differently-priced product items); *full parent + fee-only children on a custom order type* (Acowebs, Bayna, MagePeople — the parent keeps everything including the full total); *one order* (SR Partial Payments, every POS). The closest thing to a zero-total parent is Order Splitter's emptied original — and that plugin's response is to `DELETE` its `wc_order_stats` row outright rather than let it sit in the reports.

### Traps, with the observed consequence

1. **A child `shop_order` with a positive total is read by Analytics as a refund in two places.** The Segmenter emits `SUM( CASE WHEN parent_id != 0 THEN total_sales END ) AS refunds` (`Segmenter.php:75`) and the Orders report's `refunds=all` filter is literally `parent_id != 0` (`Reports/DataStore.php:1087`). A sub-order holding a tender amount shows as a **positive refunds figure** in every segmented view. (§3)
2. **The same child is half-counted in the headline metrics** — it adds to Total sales, Net sales, Taxes, Shipping and Items sold, but not to Orders count or Gross sales (`Orders/Stats/DataStore.php:107-131`). A £100 sale split £60 cash / £40 card as a £0 parent plus two children reports **Orders count 1, Gross sales £0, Net sales £100**: two headline figures that disagree by construction. This is not hypothetical — YITH and WooCommerce Deposits both hit the Net-vs-Gross divergence today, and it is what [woocommerce-admin#4050](https://github.com/woocommerce/woocommerce-admin/issues/4050) reports.
3. **"Reporting shows the payment method totals" is not a WooCommerce capability under any structure.** Core has no payment-method dimension in Analytics or in the legacy reports (0 grep hits, §3). Every POS surveyed therefore ships its own report — and Oliver's and Jovvie's still `GROUP BY payment_method`, so their splits collapse to one "Split Payment" bucket even in their own numbers. A per-tender total has to come from a per-tender record, not from a per-order column.
4. **A custom order status is a hole in a blacklist, not a way out of the reports.** Five distinct statuses are registered across the deposits plugins (`partial-payment`, `scheduled-payment`, `partially-paid` ×2, `deposit`); **none** is added to `wc_get_is_paid_statuses` and **none** is added to Analytics' excluded list — so all of them count as revenue by default (`Settings.php:318`, §3). Meanwhile the reduce-stock hooks fire only on `processing`/`completed`/`on-hold`/`payment_complete`, so an order parked in a custom status reduces no stock and is not `is_paid()`.
5. **A custom order *type* is the only thing core reliably hides from Analytics** — `sync_order()` accepts `shop_order` and `shop_order_refund` and nothing else (`Orders/Stats/DataStore.php:499-501`). That is how `shop_subscription` and the Acowebs/Bayna/MagePeople instalment children stay out of revenue. Note the `exclude_from_order_*` flags on `wc_register_order_type()` are **legacy-reports-only** and Analytics never reads them — Bayna and MagePeople left them off/commented and consequently double-count in the legacy reports while Analytics is unaffected either way.
6. **Only one order can drive a given tender's automated refund**, because `wc_refund_payment()` resolves the gateway from that order's own scalar `payment_method` (`wc-order-functions.php:764-798`). Observed consequence: **not one of the six deposits/splitter plugins has a `wc_create_refund` call at all**, and the official Woo Deposits docs say refunds are manual. Among POS plugins only FooSales attempts per-tender refunds, and only its Square/Stripe legs actually reverse.
7. **Nothing in core hides a child order from the merchant or the customer.** Both Orders list tables show children as ordinary top-level rows with their own numbers, and core has no "related orders" UI and no `WC_Order::get_related_orders()` (§3). Every plugin that splits builds that UI itself — Subscriptions' Related Orders metabox, YITH's "My Deposits" table, Acowebs's parent-number-on-thank-you override, WooCommerce Deposits' `woocommerce_my_account_my_orders_query` filter that hides `scheduled-payment` rows.
8. **Accounting connectors see one `payment_method` per order and nothing else.** Woo's own Xero extension routes *every* gateway to one account; MyWorks maps one bank account per active payment method (§3). Splitting money across orders is the only structure either can resolve into two clearing accounts; a tender breakdown in order meta is invisible to both — which is exactly the state Oliver, Jovvie, FooSales and WebPOS leave a store in.

### Ideas worth taking, as observed

- **Subscriptions' answer to "N payments, N gateways" is N *independent* top-level orders with `parent_id = 0`, joined by meta, plus a plugin-owned Related Orders UI.** It deliberately does not put `parent_id` between two `shop_order`s. It is the only surveyed model with no reporting distortion; the price is that one purchase appears as N orders everywhere.
- **`parent_id` between orders means, in core's own reading, "this row corrects that row".** Refund joins, the `refunds` filter and the Segmenter are all consistent about it. Using it for "this row is part of that row" fights three separate pieces of core SQL.
- **Order Splitter is the existence proof that the double-count is real and repairable**: it hooks `woocommerce_analytics_update_order_stats` and `DELETE`s the redundant `wc_order_stats` row, then fixes the product/coupon/tax lookups and calls `ReportsCache::invalidate()`. The documented, less violent seam for the same job is `woocommerce_analytics_update_order_stats_data` (`Orders/Stats/DataStore.php:573`), which can rewrite an order's `parent_id` and totals before they are written.
- **FooSales is the only Woo plugin found that makes a tender a first-class record** — a `foosales_payment` CPT, one post per tender, with cashier, transaction id, amount, paid and refunded flags — and it is consequently the only one whose payment report and per-tender refund work off the tenders rather than off `payment_method`. Jovvie is the only one that decomposes a split into its cash-drawer ledger (`is_split_payment` on a till event).
- **Both mainstream POS platforms model tenders as a collection on one order, never as sibling orders.** Square: `order.tenders[]`, one `Tender` per split payment, each with `type` (`CARD`/`CASH`/…), `amount_money`, `payment_id`, `tip_money`, `processing_fee_money` ([Tender](https://developer.squareup.com/reference/square/objects/Tender), [Retrieve Orders](https://developer.squareup.com/docs/orders-api/manage-orders/retrieve-orders)). Shopify: `Transaction` is a child of `Order`, up to 100 per order, each with its own `gateway`, `amount`, `currency` and `kind` (`authorization`/`capture`/`sale`/`void`/`refund`), and a refund transaction points at its capture/sale via `parent_id` ([Transaction](https://shopify.dev/docs/api/admin-rest/latest/resources/transaction)). Neither platform's order count changes when a sale is split.
- **The plumbing for a parent/child model does exist and is queryable**: `wc_get_orders(['parent'=>N])` and `GET wc/v3/orders?parent[]=N` / `parent_exclude[]=N` behave identically on CPT and HPOS, and `parent_id` is writable over REST (§3). It is only the *reporting* semantics of that column that are already spoken for.
