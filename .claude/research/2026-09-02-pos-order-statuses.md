# POS custom order statuses (`pos-open` / `pos-partial`) vs `pending` + `checkout-draft`

Wayfinder research for [wcpos/roadmap#138](https://github.com/wcpos/roadmap/issues/138) on the payments-contract map ([#97](https://github.com/wcpos/roadmap/issues/97)). Written 2026-09-02 against woocommerce-pos `main` @ `e1f3adfe`, monorepo `main` @ `7962542a6f`, WooCommerce 10.4.3 (local wp-env copy), and the gateway versions listed in §1. Every claim below is a code read, not a live test, unless it says otherwise.

## TL;DR

**Keep the custom statuses, but stop letting gateways see them.** `pos-open` is a *cart* status and earns its keep (exact till sync, its own admin tab, immunity from everything in the ecosystem that garbage-collects `pending`). The cost Paul named — gateways that expect `pending → processing/completed` — is real but narrow: across six upstream gateways, six wcpos terminal extensions and the three core offline gateways, exactly **one** functional breakage exists (Stripe refuses every asynchronous completion path — 3DS return, redirect methods, webhooks — for a non-`pending` order) and it is closed by one sanctioned filter. Everything else that misfires today is the *long tail* of `woocommerce_order_status_pending_to_*` listeners, which no filter can rewrite: WooCommerce's own customer "Processing"/"On-hold" emails never fire for a POS order, and Smart Coupons store credit needed a bridge extension.

The smallest change that fixes the whole class, not just the surveyed instances, is a **two-status protocol**: the order is `pos-open` while it is a cart on the till, and WCPOS flips it to `pending` at the moment payment begins (the checkout lane / payment template load), so every gateway, email and third-party hook sees the canonical transition. If the cashier backs out, it flips back. Two of the surveyed gateways already do this flip themselves (Stripe vouchers, all PayPal local APMs `update_status('pending')` on redirect), so the app already has to tolerate a cart coming back as `pending`.

`checkout-draft` is **not** a candidate: core deletes it after 24 hours, hides it from the "All" orders list, and its own Store API flips it to `pending` before any gateway runs — it is a Store-API implementation detail, not a "held order" concept.

Recommendation, in order of size:

1. **Now (1.10.x, no design change):** add the two missing declarations — `wc_stripe_allowed_payment_processing_statuses` and core's `woocommerce_order_is_pending_statuses` — to `includes/Orders.php`. Closes the only confirmed gateway breakage and makes core's order-pay/Store API treat `pos-open` as "stock is held" instead of re-validating stock as if it were a failed order.
2. **With the payments ledger (map #97):** adopt the two-status protocol above. `pos-partial` then becomes a projection the ledger owns (paid < total), and it too flips to `pending` when the next tender starts.
3. **Do not** migrate to `pending` + meta wholesale: it trades a bounded list of hooks for an unbounded one (every "cancel/remind pending orders" tool in the ecosystem) and costs a data migration plus an app/plugin dual-status window for no benefit the two-status protocol does not already deliver.

## §1 Gateway transition assumptions

WCPOS already declares `pos-open`/`pos-partial` payable through `woocommerce_valid_order_statuses_for_payment` and `…_for_payment_complete`, forces `needs_payment()` true for zero-total POS orders, and routes `payment_complete()` to the per-gateway configured status (`includes/Orders.php:58-64,101-157`). So `$order->needs_payment()`, `$order->payment_complete()`, `WC_Form_Handler::pay_action` (`class-wc-form-handler.php:436,456` — `needs_payment()` only) and every gateway that gates on `is_paid()` already work from a custom status. The survey therefore looked only for **direct** status reads.

Versions read: WooPayments 11.1.0 `d0eae22`; Stripe 10.9.1 `084f8bd`; PayPal Payments 4.1.2 `06f71c9`; Square, Mollie, SumUp — see the rows; wcpos terminal extensions at `main` (stripe `101b949`, sumup `e62714d`, square `8e9d4f8`, mollie `7161fbd`, payarc `104fab8`, paypal-reader `9a306ce`); WooCommerce core gateways 10.4.3.

Two cross-cutting observations from the extension survey:

- **All six terminal extensions charge `$order->get_total()`** (stripe `AjaxHandler.php:126`, sumup `Services/ReaderService.php:110`, square `AjaxHandler.php:109`, mollie `Services/MolliePaymentService.php:47`, payarc `Services/PayArcPaymentService.php:316`, paypal-reader `AjaxHandler.php:94`), and Mollie/PayPal hard-verify the captured amount equals it. That is only correct for `pos-partial` because the partial-cash path rewrites the order total to the balance and books the tender as a negative fee (`includes/Gateways/Cash.php:301-318`). Whatever the ledger design (#97) does with that hack, the extensions' "remaining balance" is `get_total()` — a ledger that keeps the true total on the order must give them a different number.
- Gateways treat `pending` as *their* status: Stripe vouchers and every PayPal local APM `update_status('pending')` mid-flow. A `pos-open` order can therefore come back `pending` today; the app's payment webview already lists `pending` among unpaid statuses (`packages/core/src/screens/main/pos/checkout/components/payment-webview.tsx:47`) but its server-truth poll only runs while the local status is `pos-open` (`:201`).

**What WCPOS patches today** (`includes/Orders.php`): `woocommerce_order_needs_payment` (zero-total only, `:101-108`), `woocommerce_valid_order_statuses_for_payment` (`:118-123`), `…_for_payment_complete` (`:133-138`), `woocommerce_payment_complete_order_status` (`:151-157`), the three offline-gateway status filters (`:167-181`), and — pending in [#1835](https://github.com/wcpos/woocommerce-pos/pull/1835) — `woocommerce_analytics_excluded_order_statuses`.

**What remains unpatched:** (1) `wc_stripe_allowed_payment_processing_statuses` (above). (2) Core's `woocommerce_order_is_pending_statuses` — `wc_get_is_pending_statuses()` (`includes/wc-order-functions.php:151-159`) is what the order-pay shortcode (`includes/shortcodes/class-wc-shortcode-checkout.php:129`) and the Store API (`src/StoreApi/Utilities/OrderController.php:712`) use to decide "stock is held, skip the re-check"; a `pos-open` order fails that test and is re-validated like a *failed* order — `woocommerce_pay_order_product_in_stock` throws "Sorry, X is no longer in stock" (`:154-157`) and the held-stock arithmetic follows (`:163`). WCPOS's own payment template (`includes/Templates/Payment.php:160-205`) bypasses the shortcode, so this only reaches merchants who pay a POS order through the stock order-pay URL or a Store-API checkout, but WooPayments' duplicate-prevention also reads it (`:179`). (3) Mollie's four status-write filters and the Mollie terminal sweeper. (4) Gateway writes with no filter at all — SumUp `failed`, Square's fulfillment poller — which only `woocommerce_before_order_object_save` could intercept; not worth it. (5) The `pending_to_*` long tail — see §2.

Read across the nine, the pattern is consistent: **gateways gate on `needs_payment()`/`is_paid()`/`payment_complete()` (filtered, fine) but *write* literal `pending`/`on-hold`/`failed`** when a payment is deferred, cancelled or declined (Stripe vouchers, all PayPal APMs, Mollie delayed methods and cancel/expire webhooks, SumUp declines). A `pos-open` order therefore already leaves `pos-open` mid-checkout on every one of those paths; the till has to cope with `pending` coming back regardless of what this ticket decides.

**What Woo's own tooling would then do to POS carts:**

- `woocommerce_cancel_unpaid_orders` / `wc_cancel_unpaid_orders()` — runs only when stock management is on and `woocommerce_hold_stock_minutes` ≥ 1; selects `wc-pending` orders older than the hold time, and then cancels only if `apply_filters('woocommerce_cancel_unpaid_order', 'checkout' === $order->get_created_via(), $order)` (`includes/wc-order-functions.php:1116-1123` in 10.4.3; trunk widens the default to `created_via IN ('checkout','store-api')`, `:1152`). **POS carts are safe by default** — core already uses `created_via` as the discriminator, which is the strongest precedent for the meta approach. Any third-party "cancel/delete stale pending orders" plugin that queries by status does not carry that guard.
- Hold-stock / reserved stock — core reserves stock only from its own checkout (`wc_reserve_stock_for_order` in `WC_Checkout`/Store API); a POS `pending` order would not reserve unless WCPOS does (it does, when prevent-overselling is on), and its reservations would then count in core's `wc-pending` query automatically (#5).
- `woocommerce_order_status_pending` actions — `wc_update_coupon_usage_counts` (`wc-order-functions.php:1067`) and `wc_maybe_increase_stock_levels` (`wc-stock-functions.php`) fire whenever an order *enters* `pending`. Reopening a paid POS order would restore stock and release coupon usage automatically (today `pos-open` does neither; re-completing is idempotent via `_order_stock_reduced` so nothing double-counts). Arguably correct, but a behaviour change to document.
- Customer-facing — My Account shows "Pay" for any order where `needs_payment()` is true. Already true for `pos-open` via WCPOS's filter, so no change.
- Abandoned-cart tooling — the mainstream products (CartFlows Cart Abandonment Recovery, Mailchimp, Klaviyo) key on the WC session/cart, not on orders. The "pending order reminder / follow-up email" class of plugins queries `wc-pending` by status and would email a customer attached to a till cart. Class-level risk, not verified per product.
- `checkout-draft` cleanup — irrelevant under `pending`; see §3 for why it rules out `checkout-draft`.

So it *is* in `wc_get_order_statuses()` (it even appears in the order-edit status dropdown, `includes/admin/meta-boxes/class-wc-meta-box-order-data.php:432-438`) and is hidden from the "All" list purely by the post-status flag (`src/Internal/Admin/Orders/ListTable.php:567-581`; CPT `class-wc-admin-list-table-orders.php:646-655`). Under HPOS, `wc_get_orders(status='any')` drops `exclude_from_search` statuses too (`OrdersTableQuery.php:693-697`).
- Payable only because DraftOrders itself appends it to `woocommerce_valid_order_statuses_for_payment[_complete]` at priority 999 (`DraftOrders.php:45-46,166-169`) — the same trick WCPOS uses. It is **not** in `wc_get_is_pending_statuses()` (`includes/wc-order-functions.php:151-160`) and **not** editable (`WC_Order::is_editable()` = `pending, on-hold, auto-draft`, `class-wc-order.php:1707-1716`).
- Core never runs a gateway against it: the Store API checkout sets `pending` *before* `process_payment` (`src/StoreApi/Routes/V1/Checkout.php:675`). Its reserved-stock query is a literal `IN ('wc-checkout-draft','wc-pending')` (`src/Checkout/Helpers/ReserveStock.php:275-278`).
- Lifecycle: **hard-deleted after one day** by `delete_expired_draft_orders()` (`DraftOrders.php:179-207`, daily `woocommerce_cleanup_draft_orders`, `date_modified <= -1 DAY`, `delete(true)`). `wc_cancel_unpaid_orders()` never touches it (queries `wc-pending` only, `class-wc-order-data-store-cpt.php:561`, `OrdersTableDataStore.php:1210-1218`).
- Hooks/emails: `woocommerce_new_order` is suppressed on create for `auto-draft/draft/checkout-draft` and fired on the first save that leaves that set (`class-wc-order-data-store-cpt.php:113,232-243`; `OrdersTableDataStore.php:2992,3093-3103`) — a genuinely useful "this is now a real order" signal that `pos-open` does not get. `status_transition()` fires the `<from>_to_<to>` hooks for every transition but skips the "status changed" note when the from-status is a draft (`class-wc-order.php:457-478`). The email trigger list is literal (`includes/class-wc-emails.php:104-120`), so `checkout-draft_to_processing` sends no new-order email — core avoids that by the draft→pending flip.
- Analytics: excluded by *filter*, not construction — DraftOrders appends it to `woocommerce_analytics_excluded_order_statuses` (`DraftOrders.php:44`); the scheduler imports it into `wc_order_stats` regardless (`OrdersScheduler.php:352-404`) and the exclusion is applied at query time (`src/Admin/API/Reports/DataStore.php:844-848,1402-1410`). Exactly the mechanism #1835 uses.

Verdict: `checkout-draft` is the Store API's scratch space for a cart that is about to be paid *in the same session*; it is hidden, short-lived and never payable. It is not a home for a POS cart that can be parked for days, must be visible to staff, and must be payable from where it sits. Notably, three of the four surveyed POS plugins avoid having an order at all until the sale is committed (and the fourth copied WCPOS). WCPOS's "the cart *is* an order from the first item" model is the outlier — which is precisely why it needs a status the rest of Woo does not act on.

## §4 Migration cost both ways

### If the custom statuses go (move to `pending` + `created_via` + cart flag)

- **Data:** a one-shot upgrade routine rewriting `wc-pos-open` → `wc-pending` (+ `_pos_cart=1`) and `wc-pos-partial` → `wc-pending` (+ ledger meta), on both storages, batched (large stores carry thousands of abandoned `pos-open` rows). It must run *before* the statuses are unregistered: an order in an unregistered status still loads, but disappears from every admin tab, is not editable, and `wc_get_order_status_name()` returns the raw slug.
- **Dual-status window:** older apps (1.10.x) keep creating `pos-open`; the plugin must accept it on write and normalise for at least one app major. The app's open-orders query, write hold, settlement hook and status pill all change (§2 #1-3, 11), and e2e teardown that finalises `pos-open` carts (`apps/main/e2e/order-cleanup.ts:58`).
- **Behaviour changes to document:** stock/coupon release on reopen; loss of the admin tabs; exposure to third-party pending-order cleanup and reminder tooling.
- **Extensions:** the Smart Coupons bridge and the Emails re-triggers are deleted (wins); the six terminal extensions are untouched.
- **Analytics:** #1835 becomes unnecessary; historic `wc_order_stats` rows for POS carts were never imported (excluded status) so nothing to re-import.

### If the statuses stay — the minimum filter set

For every surveyed gateway to treat `pos-open`/`pos-partial` exactly like `pending`:

1. `woocommerce_valid_order_statuses_for_payment` — have.
2. `woocommerce_valid_order_statuses_for_payment_complete` — have.
3. `woocommerce_payment_complete_order_status` — have.
4. `woocommerce_{cod,bacs,cheque}_process_payment_order_status` — have.
5. `woocommerce_order_needs_payment` (zero-total) — have.
6. **`woocommerce_order_is_pending_statuses`** — add. Makes `wc_get_is_pending_statuses()` include the POS statuses: core order-pay and Store API skip the failed-order stock re-check, WooPayments' duplicate-prevention sees them as pending.
7. **`wc_stripe_allowed_payment_processing_statuses`** — add. The only confirmed gateway breakage.
8. `woocommerce_analytics_excluded_order_statuses` — #1835.
9. Mollie terminal `PaymentSweeper.php:68` — add the POS statuses in the extension.
10. Optional, only if the till must keep owning a deferred/cancelled Mollie payment: `mollie-payments-for-woocommerce_initial_order_status`, `…_order_status_cancelled`, `…_order_status_expired` returning `pos-open` for `created_via === 'woocommerce-pos'`. (Not recommended — see the two-status protocol below; letting the order become `pending` and having the till list it as "awaiting payment" is simpler than fighting each gateway's writes.)

That set covers every direct status read found. What it cannot cover is the `woocommerce_order_status_pending_to_*` hook family (core customer emails, Smart Coupons, and any plugin that binds to those names), because those are hook *names*, not filterable lists. Options for that tail: (a) keep bridging case by case (today's approach — the Emails and Smart Coupons bridges, and now the customer-processing/on-hold email gap); or (b) the **two-status protocol** — flip `pos-open` → `pending` when payment begins, so the transition the tail listens for actually happens. (b) is a small change: one `update_status('pending')` at the start of the checkout lane / payment template (with the cart flag preserved so the till still owns the order), a flip back to `pos-open` on cancel, and the app tolerating `pending` as "in checkout" (§2 #3 — needed anyway for gateway rewrites). It makes rows 6-7 and the Mollie sweeper moot for the payment path, and lets the bridges in `Emails.php` and the Smart Coupons extension be deleted once no order is ever paid from a custom status.

Not verified live: everything above is from source; the Stripe 3DS refusal and the missing customer-processing email are the two claims most worth reproducing on a wp-env before 1.11 planning locks.
